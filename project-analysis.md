## 2. Database Analysis

There is **no hand-written schema** (`database/schema.sql` is an empty
placeholder). The schema is generated by Hibernate from the JPA entities
(`spring.jpa.hibernate.ddl-auto: update`). The tables below are reconstructed
from the `@Entity`/`@Table`/`@Column` annotations.

### Table: `users` (entity `AppUser`)

User accounts (both regular users and the seeded admin).

| Column | Type | Nullable | Purpose |
| ------ | ---- | -------- | ------- |
| id | BIGINT (IDENTITY) | No | PK |
| username | VARCHAR | No (unique) | Login identifier |
| password | VARCHAR | No | BCrypt hash |
| name | VARCHAR | No | Display / holder name |
| email | VARCHAR | Yes | OTP target, bank match key |
| role | VARCHAR | No | `USER` or `ADMIN` |
| status | VARCHAR | No | `ACTIVE`, `INACTIVE`, `PENDING`, `LOCKED` |
| account_id | BIGINT | Yes | FK-by-value to `accounts.id` (null until bank linked) |
| created_date | DATETIME | Yes | Set by `@PrePersist` |
| last_modified_date | DATETIME | Yes | Set by `@PreUpdate` |
| created_by | VARCHAR | Yes | `otp-verified` / `system` |
| approved_by | VARCHAR | Yes | `otp-verified` / `system` |
| approved_date | DATETIME | Yes | |
| reward_points | BIGINT | Yes | Spendable reward balance |

- **Constraints:** PK `id`; UNIQUE `username`.

- **Used by:** `AccountRepository`; `AccountService`, `TransferService`, `RewardService`, `UserService`.

### Triggers / Stored Procedures / DB Indexes

- **Triggers:** **Not Implemented** (no DB triggers; timestamping/UUIDs are done in JPA lifecycle callbacks).

## 3. Registration Flow (3-step signup)

Signup is split across three endpoints. Bank linking is deliberately deferred to *after* login (see §9).

```
SignupComponent
↓  AuthService.verifyAccount()      → POST /api/v1/auth/signup/verify-account   (sends OTP)
↓  AuthService.verifySignupOtp()    → POST /api/v1/auth/signup/verify-otp       (checks OTP)
↓  AuthService.setPassword()        → POST /api/v1/auth/signup/set-password     (creates user + auto-login)
AuthController → UserService.completeSignup() → UserRepository.save() → users table
```

### Step 1 — `POST /api/v1/auth/signup/verify-account`
- **File/Method:** `AuthController.verifyAccount`
- **Input:** `VerifyAccountRequest { username, email }` (`@NotBlank`, `@Email`)
- **Validations:** `userRepository.existsByUsername` (reject duplicate username); `existsByEmailIgnoreCase` (reject duplicate email).
- **Action:** `otpService.generateAndSendOtp(email, "SIGNUP")`.
- **Output:** `OtpResponse { message, email(masked), success }`.
- **Exceptions:** `IllegalArgumentException` → 422 (`VAL-422`).
- **DB:** upsert into `otp_tokens`.
- **Security:** public endpoint (`/api/v1/auth/**` permit-all).

### Step 2 — `POST /api/v1/auth/signup/verify-otp`
- **File/Method:** `AuthController.verifySignupOtp`
- **Input:** `VerifyOtpRequest { email, otp, purpose }`
- **Validation:** `otpService.verifyOtp(email, otp, "SIGNUP")` (purpose match, not expired, value match). Invalid → `IllegalArgumentException` (422).
- **DB:** on success the OTP row is **deleted** (consumed).
- **Output:** `OtpResponse` instructing the user to set a password.

### Step 3 — `POST /api/v1/auth/signup/set-password`
- **File/Method:** `AuthController.setPassword` → `UserService.completeSignup`
- **Input:** `SetPasswordRequest { username, email, name, password }`
- **Validations (service):** re-check `existsByUsername` and `existsByEmailIgnoreCase`.
- **DB op:** build `AppUser` with `role=USER`, `status=ACTIVE`, `accountId=null`, `password=bcrypt(password)`, `createdBy/approvedBy="otp-verified"`; `userRepository.save`.
- **Auto-login:** controller loads `UserDetails`, mints access + refresh JWT (accountId null), returns **`AuthResponse`** with HTTP `201 CREATED`.
- **Security checks:** none beyond OTP having been verified earlier. There is **no admin approval step** for users.

> **Note:** `SignupRequest` (with `initialBalance`) exists in the DTO package but is **not used** by the current 3-step flow — it is legacy. Initial balance now comes from the linked `bank_details` record.

## 4. OTP Verification Flow

```
User enters OTP → AuthService.verify*Otp() → AuthController → OtpService.verifyOtp() → otp_tokens → response
```

Owned by `OtpService` (+ async `EmailService`).

### OTP Generation
- **Method:** `OtpService.generateAndSendOtp(email, purpose)`
- **Length:** 6 digits — `String.format("%06d", secureRandom.nextInt(1000000))`.
- **Randomization:** `java.security.SecureRandom`.

### OTP Storage
- **Table:** `otp_tokens` — **one row per email** (`findTopByEmailOrderByIdDesc` then update, else insert). Columns: `otp`, `purpose`, `expires_at`.
- **Expiry:** `now + app.otp.expiration` (default **300 s = 5 min**).

### OTP Validation (`OtpService.verifyOtp`) — checks in order
1. Row exists for email → else `false`.
2. `purpose` matches → else `false`.
3. `isExpired()` (`now > expires_at`) → else `false`.
4. `otp` string equals → else `false`.
5. On success: **delete** the row (single-use), return `true`.

### Expiry Validation
`OtpToken.isExpired()` = `LocalDateTime.now().isAfter(expiresAt)`.

### Resend Flow
Re-calling step-1 endpoints re-runs `generateAndSendOtp`, which **overwrites** the same row with a fresh OTP and new expiry. There is **no resend-specific endpoint or cooldown** — **Not Implemented** (rate limiting absent).

### Success Flow
Controller proceeds (creates user / issues JWT / resets password).

### Failure Flow
`verifyOtp` returns `false` → controller throws `IllegalArgumentException` → `GlobalExceptionHandler` → **422 `VAL-422`** `"Invalid or expired OTP"`.

## 5. Login Flow (2-step user login + direct admin login)

```
LoginComponent
↓ AuthService.loginStep1()      → POST /api/v1/auth/login            (credentials → send OTP)
↓ AuthService.loginVerifyOtp()  → POST /api/v1/auth/login/verify-otp (credentials + OTP → JWT)
```

### Step 1 — `POST /api/v1/auth/login`
- **File/Method:** `AuthController.loginStep1`
- **Input:** `LoginOtpRequest { username, password }`
- **Password validation:** `authenticationManager.authenticate(UsernamePasswordAuthenticationToken)` → `DaoAuthenticationProvider` → `CustomUserDetailsService.loadUserByUsername` + `BCryptPasswordEncoder.matches`.
- **User lookup:** `userRepository.findByUsername`.
- **Action:** `otpService.generateAndSendOtp(email, "LOGIN")`.
- **Output:** `OtpResponse` (masked email).
- **Errors:** bad password → `BadCredentialsException` → **401 `AUTH-401`** "Invalid username or password".

### Step 2 — `POST /api/v1/auth/login/verify-otp`
- **File/Method:** `AuthController.loginVerifyOtp`
- **Input:** `LoginVerifyRequest { username, password, otp }`
- **Logic:** re-authenticate credentials → `verifyOtp(email, otp, "LOGIN")` → derive role from authorities → mint tokens.
- **JWT Generation:** `jwtUtil.generateToken(userDetails, role, accountId)` + `generateRefreshToken`.
- **JWT Claims:** `sub`=username, `role`, `accountId`, `tokenType=access`, `iat`, `exp`.
- **Expiration:** access **600000 ms (10 min)**; refresh **604800000 ms (7 days)**.
- **Response:** `AuthResponse { token, refreshToken, username, role, accountId, holderName, expiresIn }`.
- **Errors:** invalid OTP → 422; bad credentials → 401.

### Admin login — `POST /api/v1/auth/admin/login` (no OTP)
`AuthController.adminLogin`: authenticate → assert `ROLE_ADMIN` (else `BadCredentialsException`) → mint tokens with `accountId=null`, `role=ADMIN`.

### Sequence (user login)
```
User → LoginComponent → AuthService.loginStep1 → POST /auth/login
  → AuthController → AuthenticationManager → CustomUserDetailsService (+BCrypt)
  → OtpService.generateAndSendOtp → EmailService(@Async) → Gmail SMTP
  → OtpResponse (masked email)
User enters OTP → AuthService.loginVerifyOtp → POST /auth/login/verify-otp
  → AuthController → AuthenticationManager → OtpService.verifyOtp (delete row)
  → JwtUtil.generateToken/generateRefreshToken → AuthResponse(JWT) → persistSession()
```

## 6. JWT Authentication Flow

### JWT Creation
- **File:** `config/JwtUtil.java`
- **Methods:** `generateToken(userDetails, role, accountId)` (access), `generateRefreshToken(userDetails)` (refresh, only `tokenType=refresh` + subject), `createToken(...)`.
- **Signature:** HS256 via `Keys.hmacShaKeyFor(secret.getBytes())`. Secret in `app.jwt.secret` (`application.yaml`).

### JWT Validation
- **File:** `config/JwtUtil.java` — `validateToken` (username match + `tokenType=access` + not expired); `validateRefreshToken` (same with `tokenType=refresh`).
- **Filter:** `config/JwtAuthFilter` (`OncePerRequestFilter`).

### Security Filter Chain
```
Request
↓ CorsFilter (CorsConfig)
↓ JwtAuthFilter            (reads "Authorization: Bearer", validates, sets SecurityContext)
↓ Spring Security authorization (SecurityConfig requestMatchers)
↓ Controller
```
- Registered via `addFilterBefore(jwtAuthFilter, UsernamePasswordAuthenticationFilter.class)`.
- Session policy: **STATELESS**. CSRF disabled.

### Filter behaviour (`JwtAuthFilter.doFilterInternal`)
1. No `Bearer ` header → chain continues unauthenticated.
2. Extract username from token; if context empty → load `UserDetails` → `validateToken` → set `UsernamePasswordAuthenticationToken` in `SecurityContextHolder`.
3. Any parsing/validation exception is caught and logged; the request continues unauthenticated (and is then rejected by authorization if the endpoint is protected).

### Claims / Expiry / Algorithm
- **Claims:** `sub`, `role`, `accountId`, `tokenType`, `iat`, `exp`.
- **Expiry:** access 10 min, refresh 7 days.
- **Algorithm:** HS256.

### Unauthorized Flow
A protected endpoint hit without valid auth → `JwtAuthEntryPoint.commence` writes **HTTP 401** JSON `{"errorCode":"AUTH-401","message":"Authentication required or token expired"}`. The Angular interceptor uses this 401 to trigger a transparent refresh-and-retry (§15).

### Refresh — `POST /api/v1/auth/refresh`
`AuthController.refreshToken`: extract username → load `UserDetails` → `validateRefreshToken` → mint **new access AND new refresh** (rotation). Failure → 401.

## 7. Money Transfer Flow (most important)

```
TransferComponent
↓ TransferService.transfer()            → POST /api/v1/transfers
↓ TransferController.transfer()
↓ TransferService.transfer()  (@Transactional)
   ├─ checkIdempotency()                 (transaction_logs.idempotency_key)
   ├─ validateTransfer()                 (amount / cashback-block / self / active / balance)
   └─ executeTransfer()
        ├─ Account.debit / Account.credit
        ├─ accountRepository.save(from), save(to)
        ├─ syncBankDetailsBalance(from), (to)
        ├─ transactionLogRepository.save(SUCCESS log)
        └─ processRewardsSafely() → RewardService.processReward()
↓ DB commit → TransferResponse (+ RewardResult)
```

### `TransferController.transfer`
- **Endpoint:** `POST /api/v1/transfers` (authenticated).
- **Input:** `@Valid TransferRequest { fromAccountId, toAccountId, amount, idempotencyKey }`.
- **Bean validation:** `fromAccountId`/`toAccountId` `@NotNull @Positive`; `amount` `@NotNull @DecimalMin 0.01 @DecimalMax 1000000.00`; `idempotencyKey` `@NotNull`. Violations → **422 `VAL-422`**.
- **Output:** `TransferResponse` (HTTP 200).

### `TransferService.transfer` (`@Transactional`)
**Step 1 — `checkIdempotency`:** `transactionLogRepository.findByIdempotencyKey`; if present → `DuplicateTransferException` → **409 `TRX-409`** (and **no** FAILED row is recorded for a replay).

**Step 2 — `validateTransfer`:**
- amount null or `<= 0` → `IllegalArgumentException` (422).
- destination == `CASHBACK_ACCOUNT_ID (9999999999)` → `IllegalArgumentException` (no transfers into the corporate account).
- `fromAccountId.equals(toAccountId)` → `IllegalArgumentException` (self-transfer).
- load both via `accountService.getAccountById` (missing → `AccountNotFoundException` 404).
- either account not `ACTIVE` → `AccountNotActiveException` → **403 `ACC-403`**.
- `fromAccount.balance < amount` → `InsufficientBalanceException` → **400 `TRX-400`**.

**Step 3 — `executeTransfer`:**
1. Re-fetch both accounts.
2. `fromAccount.debit(amount)` (re-checks balance, may throw), `toAccount.credit(amount)`.
3. `accountRepository.save(from)`, `save(to)` — optimistic lock via `@Version`.
4. `syncBankDetailsBalance` for both (mirror balance back to `bank_details` when a matching `account_number` exists; admin accounts skipped).
5. Build + save SUCCESS `TransactionLog` (UUID id, stores `idempotencyKey`).
6. `processRewardsSafely` → `RewardService.processReward` (failures swallowed/logged — a reward error never fails a valid transfer).
7. Return `TransferResponse { TransactionId, status=SUCCESS, message, debitedFrom, creditedTo, amount, reward }`.

### Tables Updated
`accounts` (×2 balances), `bank_details` (×0–2), `transaction_logs` (1 SUCCESS or 1 FAILED), `users` + `reward_ledger` (when rewarded).

### Transaction Boundaries & Rollback
- The whole `transfer()` runs in one `@Transactional`. Any exception in `executeTransfer` rolls back balance changes + the success log.
- The `catch (Exception)` in `transfer()` calls `transactionLogService.logFailedTransfer(...)` which runs in **`Propagation.REQUIRES_NEW`** (separate bean → separate transaction) so the FAILED row survives the rollback, then re-throws.
- FAILED rows store `idempotencyKey = null` so the user can retry the same key after fixing the problem.

### Exception Handling
All mapped by `GlobalExceptionHandler` (see §12 table).

### Concurrency Handling / Locking Strategy
- **Optimistic locking only**, via `@Version` on `Account`. Concurrent updates to the same account throw `OptimisticLockException` (surfaced as **500 `SYS-500`** — not specifically handled).
- **No pessimistic / `SELECT ... FOR UPDATE` locking — Not Implemented.**
- **No retry logic on lock failure — Not Implemented.**

## 8. Rewards Module Flow

Owned by `RewardService` + `RewardConstants`. Rules summary:

| Rule | Value (`RewardConstants`) |
| ---- | ------------------------- |
| Earn divisor | 1 point per ₹100 (`POINTS_EARN_DIVISOR=100`, integral division) |
| Min rewardable amount | amount **> ₹100** (`MIN_REWARDABLE_AMOUNT=100`) |
| Weekend multiplier | 2× on Sat/Sun (`WEEKEND_MULTIPLIER=2`) |
| Dedup rule | first transfer per `(from, to, date)` only |
| Redeem threshold | 500 points (`REDEEM_THRESHOLD=500`) |
| Redemption value | 1 point = ₹1 |
| Funding | corporate `CASHBACK` account id `9999999999`, seed ₹1,000,000,000 |

### Reward Accumulation — `RewardService.processReward(request, txnId)`
Called *inside* the transfer transaction (intentionally **not `@Transactional`** so it joins the caller's tx; a failure can be caught without poisoning the transfer). Steps:
1. amount ≤ ₹100 → `RewardResult.none("Transfer over ₹100 to start earning...")`.
2. self-transfer / null from → `none(null)`.
3. sender must be a registered user (`userRepository.findByAccountId(fromId)`) else `none(null)`.
4. dedupe: `rewardLedgerRepository.existsByFromAccountIdAndToAccountIdAndRewardDate(from,to,today)` → already rewarded today → `none(...)`.
5. `basePoints = amount / 100` (integral); `pointsEarned = weekend ? base*2 : base`.
6. update `user.rewardPoints += earned`, `lifetimeRewardPoints += earned`; save user.
7. insert `reward_ledger` row.
8. return `RewardResult` (with `reachedRedeemThreshold` flag when crossing 500).

### Reward Redemption — `RewardService.redeem(username, points)` (`@Transactional`)
`POST /api/v1/rewards/redeem`, body `RedeemRequest { points }` (`@NotNull @Min 1`). Logic:
- `points < 500` → `IllegalArgumentException` (min redemption).
- `points > balance` → `IllegalArgumentException`.
- user must have a linked `accountId` → else error.
- load `CASHBACK` account + user account; `amount = points` (₹, scale 2).
- `cashbackAccount.debit(amount)`, `userAccount.credit(amount)`, save both, `syncBankDetailsBalance(userAccount)`.
- write a SUCCESS `transaction_logs` row (`from = CASHBACK_ACCOUNT_ID`, `idempotencyKey = "redeem-<userId>-<millis>"`).
- `user.rewardPoints -= points`; save.
- return `RedeemResponse { redeemedPoints, amountCredited, remainingPoints, transactionId, message }`.

> In transaction history, the cashback account id is masked to `null` and labelled `"CASHBACK"` (`AccountService.maskCashbackAccount`).

### Reward Expiry
**Not Implemented** — points never expire.

### Reward Profile — `GET /api/v1/rewards/me`
`RewardController.myRewards` → `RewardService.getProfile(username)` → `RewardProfileResponse { holderName, pointsBalance, lifetimePoints, redeemThreshold, canRedeem, progressPercent, weekendBonusActive }`.

### APIs Used
`GET /api/v1/rewards/me`, `POST /api/v1/rewards/redeem`. Earning has no endpoint — it happens as a side effect of `POST /api/v1/transfers`.

## 9. Beneficiary Management Flow

> **There is no "beneficiary" entity or table.** Transfers are made directly to a
> destination account id, and the closest analogue to onboarding a counterparty
> is **linking your own bank account**. Beneficiary add/update/delete/list as
> separate concepts are **Not Implemented**. The bank-linking flow is documented
> here as the related capability.

### Link Bank Account — `POST /api/v1/users/link-bank`
- **Controller:** `UserController.linkBankAccount` (authenticated; uses `Authentication.getName()`).
- **Service:** `UserService.linkBankAccount(username, accountNumber)` (`@Transactional`).
- **Request:** `LinkBankRequest { accountNumber }` (`@NotNull`).
- **Validation rules:**
  - user must not already have a linked `accountId`.
  - `bank_details` row must exist for `accountNumber`.
  - `bankDetails.email` must equal the user's email (ownership proof from signup OTP).
  - bank record must not already be `registered`.
- **DB ops:** create `accounts` row (`id = accountNumber`, balance from bank record, `ACTIVE`); set `user.accountId` + `user.name`; mark `bank_details.registered = true`.
- **Response:** `LinkBankResponse { accountId, holderName, balance, message }`.

### Fetch account / Update / Delete
- Fetch own account: `GET /api/v1/accounts/{id}` (`AccountController.getAccount`).
- Update / delete beneficiary: **Not Implemented**.

## 10. Email Service Flow

```
OtpService.generateAndSendOtp() → EmailService.sendOtpEmail() [@Async otpMailExecutor] → JavaMailSender → Gmail SMTP
```

- **Trigger events:** signup OTP, login OTP, password-reset OTP (purposes `SIGNUP`/`LOGIN`/`RESET`).
- **Service invoked:** `EmailService.sendOtpEmail(toEmail, otp, purpose)`.
- **SMTP config (`application.yaml`):** `smtp.gmail.com:587`, STARTTLS required, auth on, ssl.trust gmail, connect/read/write timeouts 30 s. Credentials are **hard-coded in `application.yaml`** (see §13 security note).
- **Email template:** plain `SimpleMailMessage`; subject/body branch on purpose; states validity = `expiration/60` minutes.
- **Sending logic:** `@Async("otpMailExecutor")` — runs on a dedicated 2–5 thread pool (`AsyncConfig`) so SMTP latency doesn't block the HTTP request. The OTP is persisted *before* dispatch, so the API responds immediately.
- **Exception handling:** `try/catch` inside `sendOtpEmail` logs and swallows failures (the user simply never receives the mail; the API call already returned success).
- **Retry logic:** **Not Implemented.**

## 13. Security Analysis

| Concern | Status | Detail |
| ------- | ------ | ------ |
| Authentication | **Implemented** | Username/password via Spring Security `DaoAuthenticationProvider`; 2-factor OTP for user login & signup; JWT bearer tokens thereafter. |
| Authorization | **Implemented (role-based, coarse)** | `SecurityConfig` restricts admin endpoints to `hasRole("ADMIN")`; everything else under `/api/v1/**` requires authentication. |
| **Object-level authorization (IDOR)** | **Not Implemented** | Account-scoped endpoints (`/accounts/{id}`, `/balance`, `/transactions`, `/transfers` `fromAccountId`) do **not** verify the account belongs to the caller. Any authenticated user can read another account's balance/history or initiate a transfer specifying another `fromAccountId`. The JWT carries `accountId` but it is not enforced server-side. |
| JWT Security | **Implemented** | HS256, signed, 10-min access + 7-day refresh with rotation; `tokenType` distinguishes access vs refresh. **Secret is hard-coded in `application.yaml`** and is short (weak for HS256). No token revocation/blacklist. |
| Password Storage | **Implemented** | BCrypt (`BCryptPasswordEncoder`). |
| Encryption (in transit) | **Partial / Not Implemented in-app** | App speaks plain HTTP locally (`http://localhost:8080`, `:4200`); passwords are sent plaintext relying on HTTPS at deployment (frontend encryption was removed per git history). No app-layer field encryption. |
| Session Handling | **Implemented (stateless)** | `SessionCreationPolicy.STATELESS`; client stores tokens in `sessionStorage`; idle auto-logout after 10 min (frontend). |
| CSRF | **Disabled (by design)** | `csrf().disable()` — acceptable for stateless bearer-token API. |
| CORS | **Implemented** | `CorsConfig` allows origin `http://localhost:4200`, credentials true, common methods/headers. |
| SQL Injection | **Protected** | All DB access via Spring Data JPA / JPQL with bound parameters; no string-concatenated SQL except parameterless `DataSeeder` migration DDL. |
| XSS | **Mostly protected** | Angular escapes interpolated bindings by default; no `bypassSecurityTrust*`/`innerHTML` sinks observed. |
| Rate Limiting | **Not Implemented** | No throttling on login/OTP/transfer — OTP can be brute-forced/spammed. |
| Email enumeration | **Partial** | Login OTP masks email, but signup (`existsByUsername`/email) and forgot-password reveal whether an account exists via distinct error messages. |
| Audit Logging | **Partial** | `LoggingAspect` (AOP) logs every service method entry/exit/timing; `transaction_logs` is the financial audit trail. No dedicated immutable security/audit-event table. |

> **Hard-coded secrets in `application.yaml`:** DB password, Gmail app password, and the JWT secret are committed in plaintext — a deployment risk.

## 17. End-to-End Transfer Walkthrough

**Scenario:** User A (account `1001001001`, balance ₹50,000) transfers ₹10,000 to User B (account `1001001002`, balance ₹75,000). Assume a weekday, first transfer of the day for this pair.

### 1. Incoming Request Payload (`POST /api/v1/transfers`)
```json
{ "fromAccountId": 1001001001, "toAccountId": 1001001002,
  "amount": 10000.00, "idempotencyKey": "1718000000000-ab12cd34" }
```
Header: `Authorization: Bearer <access JWT>`.

### 2. JWT Validation
`JwtAuthFilter` validates the token, loads User A, sets the `SecurityContext`. (Note: server does **not** verify that `fromAccountId` belongs to User A — §13 IDOR.)

### 3–6. Validation (`TransferService.validateTransfer`)
- Idempotency key not seen before → continue.
- amount > 0; destination ≠ CASHBACK; from ≠ to.
- Both accounts exist and are `ACTIVE`.
- `50,000 ≥ 10,000` → balance check passes.

### 7. Transaction Creation & Balance Movement (`executeTransfer`)
- `A.debit(10000)` → A.balance `40,000`; `B.credit(10000)` → B.balance `85,000`.
- `accountRepository.save(A)`, `save(B)` (version bumped).
- `syncBankDetailsBalance` updates `bank_details` for `1001001001` (→40,000) and `1001001002` (→85,000).
- SUCCESS `TransactionLog` saved with new UUID + idempotency key.

### 8. Reward Calculation (`RewardService.processReward`)
- amount ₹10,000 > ₹100; sender is registered; pair not yet rewarded today.
- weekday → base = `10000 / 100 = 100` points, no 2× → **100 points**.
- User A `reward_points`/`lifetime_reward_points += 100`; `reward_ledger` row inserted.

### 9. Audit Logging
`LoggingAspect` logs each service entry/exit; `transaction_logs` SUCCESS row is the financial audit record.

### 10–11. Database Updates & Commit
Single `@Transactional` commits: `accounts` ×2, `bank_details` ×2, `transaction_logs` ×1, `users` ×1, `reward_ledger` ×1.

### 12. Response Payload
```json
{ "transactionId": "<uuid>", "status": "SUCCESS",
  "message": "Transfer completed successfully",
  "debitedFrom": 1001001001, "creditedTo": 1001001002, "amount": 10000.00,
  "reward": { "rewarded": true, "pointsEarned": 100, "weekendBonus": false,
              "pointsBalance": 100, "lifetimePoints": 100,
              "reachedRedeemThreshold": false,
              "message": "You earned 100 reward points." } }
```

### Before / During / After State

| | A balance | B balance | A points | transaction_logs | reward_ledger |
| --- | --- | --- | --- | --- | --- |
| **Before** | 50,000 | 75,000 | 0 | n | m |
| **During** | (debit→40,000, credit→85,000 within tx) | | (+100 staged) | (+1 staged) | (+1 staged) |
| **After (commit)** | 40,000 | 85,000 | 100 | n+1 | m+1 |

**Failure variant:** if A's balance were ₹5,000, `InsufficientBalanceException` rolls back all balance changes; `TransactionLogService.logFailedTransfer` (REQUIRES_NEW) writes a FAILED row (visible only to A), and the API returns **400 `TRX-400`**.

## 18. Implementation Test Questions & Answers

**Q1. How is duplicate/double-spend transfer prevented?**
A unique `idempotency_key` on `transaction_logs`. `TransferService.checkIdempotency` looks it up first; a repeat throws `DuplicateTransferException` → 409. FAILED rows store a `null` key so a fixed retry isn't blocked.

**Q2. If a transfer fails, how does the FAILED record survive the rollback?**
`TransactionLogService.logFailedTransfer` runs in a **separate bean** with `Propagation.REQUIRES_NEW`, so it commits independently of the rolled-back transfer transaction. It's called from the `catch` block in `TransferService.transfer`.

**Q3. Why is `RewardService.processReward` not `@Transactional`?**
So it **joins** the transfer's transaction rather than opening a new one. `TransferService.processRewardsSafely` wraps it in try/catch; a reward failure is logged and swallowed so it never marks the transfer rollback-only or fails a valid transfer.

**Q4. What concurrency control protects account balances?**
Optimistic locking via JPA `@Version` on `Account`. There is no pessimistic locking and no lock-failure retry — a concurrent conflict surfaces as a 500 (`SYS-500`).

**Q5. Where do reward points come from on redemption?**
A seeded corporate `CASHBACK` account (id `9999999999`, balance ₹1e9). `redeem` debits CASHBACK and credits the user (1 point = ₹1), writes a SUCCESS `transaction_logs` row, and decrements `users.reward_points`. The CASHBACK id is masked to `null`/"CASHBACK" in history.

**Q6. How are reward points earned and what are the rules?**
1 point per ₹100 (integral), amount must exceed ₹100, weekends double, and only the **first** transfer per `(from, to, date)` earns (enforced by `reward_ledger` + `existsByFromAccountIdAndToAccountIdAndRewardDate`). Points accrue only to a registered sender (`findByAccountId`).

**Q7. How does JWT auth work end-to-end?**
HS256 tokens via `JwtUtil`; `JwtAuthFilter` validates the bearer token per request and populates the `SecurityContext`. Access tokens last 10 min, refresh 7 days; `/auth/refresh` rotates both. Missing/expired → `JwtAuthEntryPoint` returns 401, which the Angular interceptor uses to refresh-and-retry transparently.

**Q8. Why two-step login but one-step admin login?**
Regular users require email OTP (2FA) after password; admins authenticate directly via `/auth/admin/login` (asserting `ROLE_ADMIN`) with no OTP and `accountId=null`.

**Q9. How is an OTP stored and consumed?**
One row per email in `otp_tokens` (reused on resend), 6-digit `SecureRandom`, 5-min expiry. `verifyOtp` checks purpose/expiry/value and **deletes** the row on success (single-use).

**Q10. How does a user get a balance and account?**
Not at signup. After login the user links a pre-existing `bank_details` record via `/users/link-bank`; the system verifies the email matches, creates an `accounts` row (id = bank account number, balance from the bank record), and marks the bank record `registered`.

**Q11. Is there an account-ownership / authorization weakness?**
Yes. Account-scoped endpoints don't verify the account belongs to the caller (IDOR). The JWT carries `accountId` but it isn't enforced — any authenticated user can query another account or set a different `fromAccountId`. (§13)

**Q12. How is transaction history visibility decided?**
`TransactionLogRepository.findVisibleByAccountId`: an account sees transactions where it is the sender, OR it is the receiver of a **non-FAILED** transaction. FAILED transfers appear only to the sender.

**Q13. What does the email/SMTP failure path look like?**
`EmailService.sendOtpEmail` runs `@Async` and catches all exceptions internally — the API already responded, the OTP is already persisted, so a mail failure just means the user doesn't receive the code. No retry.

**Q14. What's missing vs. a production system?**
Beneficiary CRUD, reward expiry, rate limiting, object-level authorization, pessimistic locking/retry, externalized secrets, DB triggers, message queue, and HTTPS at the app layer are all **Not Implemented**.

**Q15. How is the schema created?**
No DDL scripts — Hibernate `ddl-auto: update` generates tables from entities; `DataSeeder` (CommandLineRunner) seeds admin, sample `bank_details`, the CASHBACK account, backfills reward columns, and drops the legacy `otp_tokens.verified` column.
