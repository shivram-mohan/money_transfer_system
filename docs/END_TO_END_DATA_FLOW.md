# 3. Registration Flow (Signup — 3 steps + auto-login)

Signup is OTP-verified; **no admin approval needed**. After step 3 the user is **auto-logged-in** and the client lands on the dashboard.

```text
SignupComponent (3 steps)
  step 1 → AuthService.verifyAccount()  → POST /api/v1/auth/signup/verify-account → AuthController.verifyAccount() → OtpService.generateAndSendOtp(SIGNUP)
  step 2 → AuthService.verifySignupOtp()→ POST /api/v1/auth/signup/verify-otp     → AuthController.verifySignupOtp()→ OtpService.verifyOtp(SIGNUP)
  step 3 → AuthService.setPassword()    → POST /api/v1/auth/signup/set-password   → AuthController.setPassword() → UserService.completeSignup() → UserRepository.save() (users)
                                                                                  → JwtUtil.generateToken/Refresh → AuthResponse (auto-login)
  → AuthService persists session → Router.navigate(['/dashboard'])
```

### Step 1 — verify account
* **File/Method:** `AuthController.verifyAccount` → `OtpService.generateAndSendOtp`.
* **Input:** `VerifyAccountRequest { username, email }`.
* **Validations:** `@NotBlank username`, `@Email email`; `userRepository.existsByUsername` and `existsByEmailIgnoreCase` must be false.
* **Output:** `OtpResponse { message, email (masked), success }`.
* **DB Ops:** upsert `otp_tokens` row (purpose `SIGNUP`).
* **Exceptions:** `IllegalArgumentException` (username/email taken) → 422 `VAL-422`.
* **Security:** public endpoint (`/api/v1/auth/**` permitAll).

### Step 2 — verify OTP
* **File/Method:** `AuthController.verifySignupOtp` → `OtpService.verifyOtp`.
* **Input:** `VerifyOtpRequest { email, otp, purpose }`.
* **Output:** `OtpResponse`. On success the OTP row is **deleted** (consumed).
* **Exceptions:** invalid/expired/purpose-mismatch → `IllegalArgumentException` → 422.

### Step 3 — set password (creates user + auto-login)
* **File/Method:** `AuthController.setPassword` → `UserService.completeSignup`.
* **Input:** `SetPasswordRequest { username, email, name, password }`.
* **Validations:** all `@NotBlank`; re-checks username/email uniqueness.
* **DB Ops:** INSERT into `users` (status `ACTIVE`, role `USER`, `account_id = null`, `reward_points = 0`, `tier = BRONZE`).
* **Output:** **`AuthResponse { token, refreshToken, username, role, accountId(null), holderName, expiresIn }`** (HTTP 201). The email was already OTP-verified, so the controller calls `userDetailsService.loadUserByUsername` + `JwtUtil` to log the user in immediately.
* **Security:** password is BCrypt-encoded before persistence.

> The bank account is **not** linked at signup — it is a separate post-login step (`POST /api/v1/users/link-bank`, see §9).

# 4. OTP Verification Flow

```text
User enters OTP → Angular (signup/login/forgot component)
  → AuthService.<verifySignupOtp | loginVerifyOtp | resetPassword>
  → POST /api/v1/auth/...
  → AuthController → OtpService.verifyOtp(email, otp, purpose)
  → OtpTokenRepository.findTopByEmailOrderByIdDesc → validate → delete on success
  → Response
```

## OTP Generation — `OtpService.generateAndSendOtp`
* **Method:** `String.format("%06d", secureRandom.nextInt(1000000))`.
* **Length:** 6 digits.
* **Randomization:** `java.security.SecureRandom`.

## OTP Storage
* **Table:** `otp_tokens`. **Columns:** `email` (unique), `otp`, `purpose`, `expires_at`, `created_at`.
* One row per email — reused on each request (`findTopByEmailOrderByIdDesc().orElseGet(new)`).

## OTP Validation — `OtpService.verifyOtp`
Checks in order: row exists → `purpose` matches → not expired (`OtpToken.isExpired()` = `now > expires_at`) → `otp` matches. Any failure returns `false` (controller throws `IllegalArgumentException`). On success the row is **deleted** so it cannot be reused.

## Expiry Validation
`expires_at = now + app.otp.expiration` (300 seconds / 5 minutes).

## Resend Flow
Each component re-calls the step-1 endpoint (`verifyAccount` / `loginStep1` / `forgotPassword`), which regenerates and re-sends a fresh OTP into the same row.

## Success Flow
`verifyOtp == true` → caller proceeds (create user / issue JWT / set new password).

## Failure Flow
`verifyOtp == false` → `IllegalArgumentException("Invalid or expired OTP")` → `GlobalExceptionHandler` → HTTP 422 `VAL-422`.

# 5. Login Flow (2 steps, OTP-gated)

## API Endpoints
* `POST /api/v1/auth/login` (step 1, credentials → OTP)
* `POST /api/v1/auth/login/verify-otp` (step 2, OTP → JWT)

## Controller / Service
* `AuthController.loginStep1`: authenticates via `AuthenticationManager.authenticate(UsernamePasswordAuthenticationToken)`, then `OtpService.generateAndSendOtp(email, "LOGIN")`. Returns `OtpResponse` with masked email.
* `AuthController.loginVerifyOtp`: re-authenticates credentials, `OtpService.verifyOtp(LOGIN)`, then builds JWT.

## Password Validation Logic
`DaoAuthenticationProvider` (`SecurityConfig.authenticationProvider`) with `CustomUserDetailsService` + `BCryptPasswordEncoder`. `CustomUserDetailsService.loadUserByUsername` loads `AppUser`, rejects non-`ACTIVE` users, and grants `ROLE_<role>`.

## JWT Generation — `JwtUtil.generateToken`
## JWT Claims
* `sub` = username
* `role` = `USER` / `ADMIN`
* `accountId` = linked account id (nullable)
* `tokenType` = `access`
* `iat`, `exp`.
Refresh token (`generateRefreshToken`) carries only `tokenType = refresh` + subject.

## Expiration Logic
Access token `app.jwt.expiration = 600000 ms` (10 min). Refresh token `app.jwt.refresh-expiration = 604800000 ms` (7 days). Signed HS256.

## Response Structure — `AuthResponse`
`{ token, refreshToken, username, role, accountId, holderName, expiresIn }`. Frontend `AuthService.persistSession` stores these in **sessionStorage**.

## Error Responses
* Bad credentials → `BadCredentialsException` → 401 `AUTH-401`.
* Invalid OTP → `IllegalArgumentException` → 422 `VAL-422`.

## Sequence Diagram (Login)
```text
User → LoginComponent.onLogin → AuthService.loginStep1
     → POST /auth/login → AuthController.loginStep1
        → AuthenticationManager.authenticate → UserRepository.findByUsername
        → OtpService.generateAndSendOtp(LOGIN) → EmailService(@Async) → SMTP
     ← OtpResponse(masked email)
User → LoginComponent.onVerifyOtp → AuthService.loginVerifyOtp
     → POST /auth/login/verify-otp → AuthController.loginVerifyOtp
        → AuthenticationManager.authenticate → OtpService.verifyOtp(LOGIN)
        → JwtUtil.generateToken + generateRefreshToken
     ← AuthResponse(token, refreshToken, ...) → persistSession → /dashboard
```

# 6. JWT Authentication Flow

## JWT Creation
* **File:** `config/JwtUtil.java`. **Methods:** `generateToken`, `generateRefreshToken`, `createToken` (signs with `Keys.hmacShaKeyFor(secret.getBytes())`, `SignatureAlgorithm.HS256`).

## JWT Validation
* **File:** `config/JwtUtil.java`. **Methods:** `validateToken` (subject matches + `tokenType=access` + not expired), `validateRefreshToken` (same with `tokenType=refresh`), `extractAllClaims` (parses with signing key).

## Security Filter Chain
```text
Request
  → CorsFilter (CorsConfig)
  → JwtAuthFilter (OncePerRequestFilter)         [config/JwtAuthFilter]
      reads "Authorization: Bearer <jwt>"
      → JwtUtil.extractUsername → CustomUserDetailsService.loadUserByUsername
      → JwtUtil.validateToken → SecurityContextHolder.setAuthentication
  → authorizeHttpRequests rules (SecurityConfig)
  → Controller
  (no/invalid token on protected route → JwtAuthEntryPoint → 401 AUTH-401)
```

## SecurityConfig authorization rules
* `/api/v1/auth/**` → permitAll
* `GET /api/v1/users`, `PUT /api/v1/users/*/activate`, `PUT /api/v1/users/deactivate`, `POST /api/v1/accounts`, `PUT /api/v1/accounts/*/activate`, `PUT /api/v1/accounts/*/deactivate`, `GET /api/v1/accounts` → `hasRole('ADMIN')`
* all other `/api/v1/**` → `authenticated()`
* Session policy: **STATELESS**. CSRF: **disabled**.

## Claims / Expiry / Algorithm / Unauthorized Flow
* Claims: `sub`, `role`, `accountId`, `tokenType`, `iat`, `exp`. Algorithm: HS256. Expiry: 10 min access / 7 day refresh.
* Unauthorized → `JwtAuthEntryPoint.commence` writes `{"errorCode":"AUTH-401","message":"Authentication required or token expired"}` with HTTP 401. The Angular `authInterceptor` keys off 401 to refresh-and-retry (see §15).

# 7. Money Transfer Flow (most important)

```text
TransferComponent.onSubmit
  → guard: self-transfer blocked client-side
  → AccountService.getAccount(toId)        (GET /accounts/{toId})  — confirm receiver name
  → ConfirmDialogComponent (shows receiver name + amount)
  → executeTransfer → TransferService.transfer (idempotencyKey generated client-side)
  → POST /api/v1/transfers
  → TransferController.transfer
  → TransferService.transfer  [@Transactional]
       1. checkIdempotency           (TransactionLogRepository.findByIdempotencyKey)
       2. validateTransfer           (amount, CASHBACK guard, self, active, balance)
       3. executeTransfer            (debit/credit, save accounts, sync bank_details, SUCCESS log)
       4. processRewardsSafely       (RewardService.processReward — never fails the transfer)
  → on any failure: TransactionLogService.logFailedTransfer (REQUIRES_NEW) → re-throw
  → TransferResponse (+ RewardResult)
```

### Step: `TransferController.transfer`
* **File:** `controller/TransferController.java`. **Input:** `@Valid TransferRequest { fromAccountId, toAccountId, amount, idempotencyKey }`. **Output:** `TransferResponse`. HTTP 200.

### Step: `TransferService.transfer` (`@Transactional`)
* **Inputs:** `TransferRequest`. **Outputs:** `TransferResponse { TransactionId, status, message, debitedFrom, creditedTo, amount, reward }`.
* **Tables updated:** `accounts` (both balances), `bank_details` (synced), `transaction_logs` (SUCCESS row; plus a cashback SUCCESS row from rewards), `reward_ledger`, `users` (reward points/tier).

### `checkIdempotency`
Looks up `idempotency_key`; if present → `DuplicateTransferException` → 409 `TRX-409`. An idempotent replay does **not** write a FAILED row.

### `validateTransfer` (ordered)
1. amount null or ≤ 0 → `IllegalArgumentException`.
2. `toAccountId == CASHBACK_ACCOUNT_ID (9999999999)` → `IllegalArgumentException` ("Transfers to this account are not allowed").
3. `fromAccountId == toAccountId` → `IllegalArgumentException` (self-transfer).
4. load both accounts (`AccountService.getAccountById` → `AccountNotFoundException` if missing).
5. source not active → `AccountNotActiveException`.
6. destination not active → `AccountNotActiveException`.
7. `fromAccount.balance < amount` → `InsufficientBalanceException`.

### `executeTransfer`
`fromAccount.debit(amount)` (re-checks balance, throws `InsufficientBalanceException` if short), `toAccount.credit(amount)`, save both, `syncBankDetailsBalance` for each, build + save SUCCESS `TransactionLog` (UUID id), then `processRewardsSafely`.

### Transaction Boundaries / Rollback
* The whole `transfer` runs in one JPA transaction. On exception it rolls back the balance/log changes.
* **FAILED logging survives rollback:** `TransactionLogService.logFailedTransfer` is `@Transactional(propagation = REQUIRES_NEW)` in a **separate bean**, so the FAILED row commits independently. It stores `idempotency_key = null` (so the user can retry).
* Rewards never roll back a transfer: `RewardService.processReward` is **not** `@Transactional` (joins caller's tx); `processRewardsSafely` swallows any reward exception and logs it.

### Exception Handling → HTTP (via `GlobalExceptionHandler`)
| Exception | Code | HTTP |
| --------- | ---- | ---- |
| `AccountNotFoundException` | ACC-404 | 404 |
| `AccountNotActiveException` | ACC-403 | 403 |
| `InsufficientBalanceException` | TRX-400 | 400 |
| `DuplicateTransferException` | TRX-409 | 409 |
| `IllegalArgumentException` | VAL-422 | 422 |
| `MethodArgumentNotValidException` | VAL-422 | 422 |
| `BadCredentialsException` | AUTH-401 | 401 |
| `Exception` (fallback) | SYS-500 | 500 |

### Concurrency Handling / Locking Strategy
* **Optimistic locking** via `@Version` on `Account`. Concurrent updates to the same account throw an optimistic-lock exception (surfaced as SYS-500). **No pessimistic/row locks** are used.

### Failed-transfer visibility rule (`TransactionLogRepository.findVisibleByAccountId`)
A FAILED transfer appears in the **sender's** history only — never the would-be receiver's. The query: account is `from_account`, OR account is `to_account` AND `status <> FAILED`. The same predicate is applied in `findByAccountIdAndDateRange`.

# 8. Rewards Module Flow

## Reward Accumulation — `RewardService.processReward` (called inside the transfer tx)
Eligibility (all must hold, else `RewardResult.none(...)`):
1. `amount > 100` (`RewardConstants.MIN_REWARDABLE_AMOUNT`).
2. `fromId != null` and `fromId != toId` (different/not self).
3. Sender is a registered user (`userRepository.findByAccountId(fromId)` present).
4. **First transfer today for this directed pair** — `rewardLedgerRepository.existsByFromAccountIdAndToAccountIdAndRewardDate(from,to,today)` must be false.

## Reward Calculation Formula
* `basePoints = floor(amount / 100)` (`divideToIntegralValue`).
* `pointsEarned = floor(basePoints × tier.multiplier)` (BRONZE 1.0, SILVER 1.5, GOLD 2.0, PLATINUM 3.0) — `applyMultiplier`, `RoundingMode.FLOOR`.
* `newPoints = currentPoints + pointsEarned`; tier re-derived via `Tier.fromPoints`.

> The brief's "2× on weekends" rule is **Not Implemented**; the multiplier is **tier-based** instead.

## Cashback — `RewardService.payCashback` (guaranteed, automatic)
* `cashbackUnits = ThreadLocalRandom(1 .. pointsEarned+1)` (random in `[1, pointsEarned]`), `cashback = units` scaled to 2dp.
* Debits the corporate **CASHBACK** account (`id 9999999999`, seeded balance ₹1,000,000,000 by `DataSeeder.seedCashbackAccount`), credits the receiver, syncs `bank_details`, writes a SUCCESS `transaction_logs` row with `idempotency_key = "cashback-" + sourceTxnId`.
* If the CASHBACK account is missing or exhausted → cashback skipped (returns 0), points still awarded.
* The CASHBACK account id is **masked** to `null`/label `"CASHBACK"` in user history (`AccountService.maskCashbackAccount`), and transfers **into** it are blocked (`validateTransfer`).

> **Manual reward redemption / donation to charity (education / medical / elderly)** as described in `gamification_rewards.txt` is **Not Implemented**. There is no redeem/donate endpoint; cashback is automatic. The frontend `reward-dialog.component` only celebrates upgrades. There is no `donations` table.

## Reward Expiry — `RewardSchedulerService` (`@Scheduled`)
There is no fixed point-expiry; instead an **inactivity downgrade**:
* `runInactivitySweep` (daily `0 0 9 * * *`): if `30+` days since `last_transaction_date` → downgrade one tier (`Tier.previous()`, points reset to that tier's `minPoints`), send downgrade email. At `30 - 10 = 20` days, send a one-time warning email (`downgrade_warning_sent` guard).
* `sendMonthlySummaries` (monthly `0 0 8 1 * *`): emails last month's summary.

## Tables Updated
`users` (points/tier/last_transaction_date/downgrade_warning_sent), `reward_ledger`, `accounts` (CASHBACK + receiver), `bank_details`, `transaction_logs` (cashback row).

## APIs Used (read side)
* `GET /api/v1/rewards/me` → `RewardController.myRewards` → `RewardService.getProfile` → `RewardProfileResponse`.
* `GET /api/v1/rewards/me/summary?month=yyyy-MM` → `mySummary` → `getMonthlySummary` → `MonthlySummaryResponse`.

## Execution Order (within a transfer)
balance debit/credit → SUCCESS log → eligibility checks → compute points → pay cashback (separate SUCCESS log) → persist user points/tier → write `reward_ledger` → return `RewardResult`.

# 9. Beneficiary Management Flow

**Not Implemented.**

There is no `Beneficiary` entity, repository, controller, service, or table. Transfers are addressed by raw account id entered in `TransferComponent`; the receiver is confirmed by a live lookup (`GET /api/v1/accounts/{id}` → holder name) shown in `ConfirmDialogComponent` before sending. The closest persistent "account ownership" feature is **bank-account linking**:

| Operation | Endpoint | Controller | Service | Repository | Tables | Validation |
| --------- | -------- | ---------- | ------- | ---------- | ------ | ---------- |
| Link bank account | `POST /api/v1/users/link-bank` | `UserController.linkBankAccount` | `UserService.linkBankAccount` | `UserRepository`, `BankDetailsRepository`, `AccountRepository` | `users`, `bank_details`, `accounts` | account must exist in `bank_details`, email must match user's, not already `registered`, user has no `account_id` yet |

* Add / Update / Delete / Fetch Beneficiaries: **Not Implemented**.

# 10. Email Service Flow

## Trigger Events
* OTP needed (signup/login/reset) → `OtpService.generateAndSendOtp` → `EmailService.sendOtpEmail`.
* Rewards scheduler → `sendMonthlySummaryEmail`, `sendDowngradeWarningEmail`, `sendDowngradeEmail`.

## Service Invoked
`service/EmailService.java` using Spring `JavaMailSender` with `SimpleMailMessage`.

## SMTP Configuration (`application.yaml`)
`spring.mail.host=smtp.gmail.com`, `port=587`, `auth=true`, `starttls.enable=true`, connect/read/write timeouts = 5000 ms. Credentials in `spring.mail.username/password`.

## Email Template
Plain-text bodies built in Java (subject + body strings per purpose: SIGNUP / RESET / LOGIN, and rewards emails). No HTML templating engine.

## Sending Logic
All send methods are `@Async("otpMailExecutor")` (pool from `AsyncConfig`: core 2 / max 5 / queue 100) so the HTTP thread is not blocked. The OTP is persisted **before** the email is dispatched.

## Exception Handling
Each method wraps `mailSender.send` in try/catch and **logs** failures (`log.error`) — a mail failure does not propagate to the caller or fail the request.

## Retry Logic
**Not Implemented** (no retry/backoff; a failed send is only logged).

# 17. End-to-End Transfer Walkthrough

**Scenario:** User A (account `1001001001`, balance ₹50,000) transfers ₹10,000 to User B (account `1001001002`). Assume first transfer of the day for this pair; both ACTIVE; A is BRONZE with 0 points.

### Before State
* `accounts[1001001001].balance = 50000.00`, `accounts[1001001002].balance = 75000.00`
* `accounts[9999999999 CASHBACK].balance = 1000000000.00`
* `users[A].reward_points = 0`, `tier = BRONZE`

### 1. Incoming Request Payload (POST `/api/v1/transfers`)
```json
{ "fromAccountId": 1001001001, "toAccountId": 1001001002, "amount": 10000.00, "idempotencyKey": "1718900000000-abc123" }
```
Header: `Authorization: Bearer <A's access token>`.

### 2. JWT Validation
`JwtAuthFilter` validates the access token, loads A via `CustomUserDetailsService`, sets the security context. `SecurityConfig` allows `/api/v1/transfers` for any authenticated user.

### 3. User Validation
Bean validation on `TransferRequest` passes (positive ids, amount within 0.01–1,000,000, idempotency key present).

### 4. Beneficiary Validation
**Not Implemented** — instead, the frontend pre-confirmed B's holder name via `GET /accounts/1001001002`. Server-side, `validateTransfer` only checks the account ids/state.

### 5. Account Validation + 6. Balance Check (`validateTransfer`)
Idempotency key unused; `toAccountId != CASHBACK`; not self; both accounts loaded & ACTIVE; `50000 ≥ 10000` ✓.

### 7. Transaction Creation (`executeTransfer`)
`A.debit(10000)` → 40000; `B.credit(10000)` → 85000; save both; sync `bank_details`; save SUCCESS `transaction_logs` row (UUID id).

### 8. Reward Calculation (`processReward`)
amount 10000 > 100 ✓, different users ✓, A is registered ✓, no ledger row for (A,B,today) ✓.
`basePoints = floor(10000/100) = 100`; BRONZE ×1.0 → `pointsEarned = 100`; `newPoints = 100` → still BRONZE.
`payCashback`: `cashbackUnits = random(1..100)` (say **₹37**) — CASHBACK debited 37 → 999,999,963; B credited 37 → 85,037; SUCCESS `transaction_logs` row `idempotency_key = "cashback-<txnId>"`.
Persist `users[A]`: points 100, tier BRONZE, `last_transaction_date = now`, `downgrade_warning_sent = false`. Insert `reward_ledger` (points 100, cashback 37, reward_date today).

### 9. Audit Logging
SUCCESS transfer row + SUCCESS cashback row in `transaction_logs`; `LoggingAspect` logs entry/exit of each service method.

### 10. Database Updates (committed in one tx, except FAILED-path logging)
`accounts` (A, B, CASHBACK), `bank_details` (B, CASHBACK if linked), `transaction_logs` (×2), `reward_ledger` (×1), `users` (A).

### 11. Commit
The `@Transactional` boundary on `TransferService.transfer` commits. (Had it failed, balances/logs roll back and a FAILED row is written in a `REQUIRES_NEW` tx.)

### 12. Response Payload
```json
{
  "TransactionId": "<uuid>",
  "status": "SUCCESS",
  "message": "Transfer completed successfully",
  "debitedFrom": 1001001001,
  "creditedTo": 1001001002,
  "amount": 10000.00,
  "reward": {
    "rewarded": true, "pointsEarned": 100, "cashbackAmount": 37.00,
    "totalPoints": 100, "tier": "BRONZE", "nextTier": "SILVER",
    "pointsToNextTier": 400, "tierUpgraded": false, "closeToNextTier": false,
    "message": "You earned 100 reward points."
  }
}
```

### After State
* `accounts[A].balance = 40000.00`, `accounts[B].balance = 85037.00`, `accounts[CASHBACK].balance = 999999963.00`
* `users[A].reward_points = 100`, `tier = BRONZE`
* `transaction_logs`: +1 SUCCESS transfer, +1 SUCCESS cashback; `reward_ledger`: +1 row.

> **Failure variant** (A sends ₹120,000 with only ₹40,000): `validateTransfer` throws `InsufficientBalanceException` → tx rolls back → `TransactionLogService.logFailedTransfer` writes a FAILED row (from=A, to=B, reason "Insufficient balance...", idempotency_key null) in a new tx → API returns 400 `TRX-400`. That FAILED row is visible in **A's** history only, not B's (`findVisibleByAccountId`).

# 18. Implementation Test Questions & Answers

**Q1. Why does a failed transfer still appear in history if the transaction rolled back?**
A. `TransferService.transfer` catches the exception and calls `TransactionLogService.logFailedTransfer`, which runs in `@Transactional(propagation = REQUIRES_NEW)` in a separate bean — so the FAILED row commits in its own transaction independent of the rolled-back transfer.

**Q2. A failed transfer A→B: whose history shows it?**
A. Only the sender (A). `TransactionLogRepository.findVisibleByAccountId` returns rows where the account is `from_account`, or is `to_account` **and** `status <> FAILED`. The same filter is in `findByAccountIdAndDateRange`.

**Q3. How is idempotency enforced, and why isn't it stored on FAILED rows?**
A. `checkIdempotency` looks up `idempotency_key` in `transaction_logs`; a hit throws `DuplicateTransferException` (409). FAILED rows store `idempotency_key = null` so the user can retry the same transfer after fixing the problem (the unique constraint would otherwise block it).

**Q4. Can a reward failure break a transfer?**
A. No. `RewardService.processReward` is not `@Transactional` (joins the caller tx), and `TransferService.processRewardsSafely` swallows and logs any reward exception. The transfer's SUCCESS commit is unaffected.

**Q5. How are reward points and the tier multiplier calculated?**
A. `basePoints = floor(amount / 100)`; `pointsEarned = floor(basePoints × tier.multiplier)` (BRONZE 1.0, SILVER 1.5, GOLD 2.0, PLATINUM 3.0). Tier is derived from lifetime points via `Tier.fromPoints`.

**Q6. What stops the same pair farming rewards repeatedly in a day?**
A. `RewardLedgerRepository.existsByFromAccountIdAndToAccountIdAndRewardDate(from,to,today)` — only the first transfer per directed (from→to) pair per calendar day earns points/cashback.

**Q7. Where does cashback money come from and how is it hidden?**
A. The seeded corporate CASHBACK account (`id 9999999999`, ₹1B float, `DataSeeder.seedCashbackAccount`). Cashback is a real account-to-account movement logged as SUCCESS. Its id is masked to `"CASHBACK"` in user history (`AccountService.maskCashbackAccount`), and transfers into it are blocked in `validateTransfer`.

**Q8. Is manual reward redemption/donation implemented?**
A. No. Cashback is automatic and guaranteed per rewarded transfer. There is no redeem/donate endpoint or donations table (the `gamification_rewards.txt` redemption/charity spec is unimplemented).

**Q9. What is the OTP lifecycle?**
A. 6-digit `SecureRandom`, one row per email (upserted), 5-min expiry (`app.otp.expiration=300`). `verifyOtp` checks existence, purpose, expiry, and value, then deletes the row (single-use).

**Q10. How does the app stay logged in past the 10-minute access token?**
A. The Angular `authInterceptor` intercepts 401s and calls `POST /auth/refresh` once (shared across concurrent requests via a `BehaviorSubject`), swapping in a new access token and retrying. Refresh tokens last 7 days; on refresh failure the user is logged out.

**Q11. What concurrency protection exists on balances?**
A. Optimistic locking via `@Version` on `Account`. There is no pessimistic locking; concurrent conflicting updates fail the second writer.

**Q12. Why is the user auto-logged-in after signup?**
A. The email is OTP-verified during steps 1–2, so `AuthController.setPassword` issues JWT tokens (`AuthResponse`) instead of a bare user DTO; the frontend persists the session and routes to `/dashboard`.

**Q13. Why did clicking "Admin Portal" log the admin out previously?**
A. The admin navbar brand linked to a non-existent route `/admin/dashboard`, which the `**` wildcard redirected to `/login`. It now links to the real route `/admin`.

**Q14. How is admin access enforced end to end?**
A. Backend: `SecurityConfig` requires `hasRole('ADMIN')` on admin endpoints; roles come from the JWT-resolved `CustomUserDetailsService` (`ROLE_ADMIN`). Frontend: `adminGuard` on `/admin*` routes and `userGuard` keeps admins off user routes.

**Q15. How is a user permitted to link a specific bank account?**
A. `UserService.linkBankAccount` requires the `accountNumber` to exist in `bank_details`, the bank record's email to match the user's OTP-verified email, the record not already `registered`, and the user to have no `account_id` yet. It then creates the `accounts` row seeded from the bank balance.

**Q16. Where is the schema defined if `schema.sql` is empty?**
A. It's auto-generated by Hibernate (`spring.jpa.hibernate.ddl-auto: update`) from the JPA entities. `database/schema.sql`/`seed-data.sql` are placeholders; runtime seeding is done by `DataSeeder`.

**Q17. What are the security gaps to be aware of?**
A. No rate limiting on OTP/login; JWT secret in `application.yaml`; no token revocation/blacklist; CSRF disabled (acceptable for stateless bearer API); no explicit CSP; email send failures are logged but not retried.

**Q18. How are exceptions mapped to HTTP responses?**
A. `GlobalExceptionHandler` (`@RestControllerAdvice`) maps each exception to an `ErrorResponse { errorCode, message, timestamp, path }` — e.g. ACC-404/404, ACC-403/403, TRX-400/400, TRX-409/409, VAL-422/422, AUTH-401/401, SYS-500/500.

**Q19. What time-based rewards jobs run, and when?**
A. `RewardSchedulerService`: monthly summary email at `0 0 8 1 * *` (08:00 on the 1st), and a daily inactivity sweep at `0 0 9 * * *` (warn at 20 days idle, downgrade one tier at 30 days idle).

**Q20. Does the app use localStorage or cookies for the session?**
A. For the **session/auth**, neither — tokens and profile fields are kept in `sessionStorage` (cleared on tab close or logout); auth is bearer-token, not cookie-based. `localStorage` is used only for the non-sensitive **UI theme preference** (`app-theme`), never for credentials (see §21).

| Functionality | How |
| ------------- | --- |
| **Pre-transfer receiver confirmation** | `TransferComponent.onSubmit` looks up `GET /accounts/{toId}` and shows the holder name in `ConfirmDialogComponent` before sending. |

## D. Rewards & gamification (detailed)

| Functionality | How |
| ------------- | --- |
| **Earning eligibility** | `RewardService.processReward` (joins the transfer tx): amount > ₹100, sender ≠ receiver/not self, sender is a registered user (`UserRepository.findByAccountId`), and it's the **first transfer today for this directed (from→to) pair** (`RewardLedgerRepository.existsByFromAccountIdAndToAccountIdAndRewardDate`). |
| **Points formula** | `basePoints = floor(amount / 100)`; `pointsEarned = floor(basePoints × tier.multiplier)`. |
| **Tiers & multipliers** | `enum Tier`: BRONZE 0+ (×1.0), SILVER 500+ (×1.5), GOLD 2000+ (×2.0), PLATINUM 5000+ (×3.0). Tier is derived from lifetime `users.reward_points` via `Tier.fromPoints` (single source of truth). |
| **Guaranteed cashback** | `RewardService.payCashback`: a random amount in `[1, pointsEarned]` (`ThreadLocalRandom`) is moved from the corporate **CASHBACK** account (id `9999999999`, ₹1B float seeded by `DataSeeder`) to the receiver and logged as a SUCCESS `transaction_logs` row (`idempotency_key = "cashback-<txnId>"`). Skipped (points still granted) if the float is missing/exhausted. |
| **CASHBACK account protection** | Transfers **into** it are blocked (`validateTransfer`); its id is masked in all history (`AccountService.maskCashbackAccount`). |
| **Reward audit ledger** | Every rewarded transfer inserts a `reward_ledger` row (points, cashback, `reward_date`) used for the daily-limit check and summaries. |
| **Tier upgrade / nudge UX** | `TransferResponse.reward` (`RewardResult`) carries `tierUpgraded`, `closeToNextTier`, progress; `TransferComponent` shows `RewardDialogComponent` to celebrate upgrades / nudge when close. |
| **Rewards profile page** | `RewardsComponent` → `/rewards/me` → `RewardService.getProfile` → `RewardProfileResponse` (points, tier, multiplier, `progressPercent`, next tier, lifetime cashback). Tier badges are the only colourful UI (`TIER_META`). |
| **Monthly summary** | `/rewards/me/summary?month=yyyy-MM` → `RewardService.getMonthlySummary` aggregates `reward_ledger` (`sumPointsEarned`, `sumCashback`, `countByUserIdAndCreatedOnBetween`). |
| **Monthly summary email (scheduled)** | `RewardSchedulerService.sendMonthlySummaries` — cron `0 0 8 1 * *` (08:00 on the 1st) emails last month's summary to every active, bank-linked user with an email. |
| **Inactivity downgrade (scheduled)** | `RewardSchedulerService.runInactivitySweep` — cron `0 0 9 * * *` (daily 09:00). If `users.last_transaction_date` is **≥ 30 days** old → downgrade one tier (`Tier.previous()`, points reset to that tier's `minPoints`), restart the clock, send a downgrade email. At **20 days** idle (30 − 10 lead) → send a one-time warning email (guarded by `downgrade_warning_sent`). BRONZE/never-transacted users are skipped. Each user is processed defensively so one failure doesn't abort the batch. |
| **Reward standing maintenance** | On each rewarded transfer, `users.reward_points`, `tier`, `last_transaction_date` are updated and `downgrade_warning_sent` reset to false. |

# 20. End-to-End Data Flow (Frontend ↔ Backend ↔ Database)

## 20.1 The layered pipeline

```text
[Angular component]                        templates bind to component state; forms (ReactiveForms) collect input
   │  calls a typed service method (Observable)
[Angular service]  (auth/account/transfer/reward/user-management)
   │  HttpClient builds the request to environment.apiUrl = http://localhost:8080/api/v1
[authInterceptor]  attaches "Authorization: Bearer <accessToken>" (from sessionStorage)
   │  (on 401 → single shared /auth/refresh → retry; see §21)
══════════════════════ network (JSON over HTTP) ══════════════════════
[CorsFilter]          CorsConfig validates origin/headers/method
[JwtAuthFilter]       parses Bearer token → JwtUtil.extractUsername → CustomUserDetailsService.loadUserByUsername
   │                  → JwtUtil.validateToken → SecurityContextHolder.setAuthentication
[SecurityConfig]      authorizeHttpRequests: permitAll / authenticated / hasRole('ADMIN')
[@RestController]     Jackson deserializes JSON → request DTO; @Valid runs Bean Validation
[@Service]            business logic, @Transactional boundary
[Spring Data JPA]     repository methods / JPQL → Hibernate
[MySQL]               SQL executes; rows mapped back to @Entity objects
   │  service maps entity → response DTO
[@RestController]     Jackson serializes DTO → JSON, ResponseEntity (status + body)
══════════════════════ network ══════════════════════
[Angular service]     Observable emits typed response
[Angular component]   updates state / navigates / shows MatSnackBar; (errors → component error handler)
```

* **Serialization:** JSON both ways via Jackson (backend) and `HttpClient` generic typing (frontend). DTOs are the contract — entities are never exposed directly except `TransactionLog` (which carries `@Transient` display fields).
* **Validation lives at the edge:** Jakarta Bean Validation annotations on request DTOs (`@NotNull`, `@Positive`, `@DecimalMin/Max`, `@Email`); failures become `MethodArgumentNotValidException` → 422 before any service code runs.
* **Transaction boundary:** opened at the `@Service` method (`@Transactional`), committed/rolled back around the repository calls; the DB sees a single unit of work (except the deliberate `REQUIRES_NEW` failed-transfer log).

## 20.2 Concrete trace — money transfer (write path)

```text
TransferComponent.executeTransfer
  → TransferService.transfer(TransferRequest)            [HttpClient POST /transfers]
  → authInterceptor adds Bearer token
  → JwtAuthFilter authenticates → SecurityConfig allows (authenticated)
  → TransferController.transfer (@Valid TransferRequest)
  → TransferService.transfer [@Transactional]
       checkIdempotency      → SELECT transaction_logs WHERE idempotency_key=?
       validateTransfer      → SELECT accounts (×2)  [AccountService.getAccountById]
       executeTransfer       → UPDATE accounts (debit), UPDATE accounts (credit)
                             → UPDATE bank_details (×, syncBankDetailsBalance)
                             → INSERT transaction_logs (SUCCESS)
       processReward         → SELECT reward_ledger (dup check) → UPDATE accounts (CASHBACK, receiver)
                             → INSERT transaction_logs (cashback SUCCESS)
                             → UPDATE users (points/tier) → INSERT reward_ledger
  ← COMMIT → TransferResponse{...,reward} → JSON
  → component: snackbar + RewardDialog + reload balance
  (exception path → ROLLBACK; TransactionLogService.logFailedTransfer INSERT (REQUIRES_NEW) → 4xx ErrorResponse)
```

## 20.3 Concrete trace — rewards profile (read path)

```text
RewardsComponent.loadRewards → RewardService.getMyRewards [GET /rewards/me]
  → JwtAuthFilter resolves principal → Authentication.getName() = username
  → RewardController.myRewards → RewardService.getProfile(username) [@Transactional(readOnly=true)]
       SELECT users WHERE username=?  → SELECT SUM(cashback) FROM reward_ledger ...
  ← RewardProfileResponse → JSON → component renders tier badges/progress
```

## 20.4 Non-HTTP flows

* **Scheduled jobs (no frontend):** `@EnableScheduling` → `RewardSchedulerService` cron jobs read `users`/`reward_ledger`, write `users`, and call `EmailService` → SMTP.
* **Async email:** controllers/services call `EmailService` `@Async` methods that run on `otpMailExecutor` threads and talk to Gmail SMTP — fully off the request thread.
* **Startup:** `DataSeeder` (`CommandLineRunner`) runs once after context load, using `JdbcTemplate` (migration DDL) and repositories (seed rows).
* **Schema:** no hand-written DDL is applied at runtime — Hibernate `ddl-auto: update` reconciles the MySQL schema to the `@Entity` classes on boot.

## 20.5 Direction-of-trust summary

* The **frontend is never trusted** for authorization or balance rules — it only improves UX (e.g. it does **not** block an over-balance transfer; the backend rejects it and logs a FAILED row).
* The **backend is the source of truth**; the **database** holds durable state; **JWT** carries identity/role between them on every call.

# 21. Client-Side Storage, Auth Guards & JWT

## 21.1 What is stored where

### sessionStorage (auth/session) — `AuthService.persistSession`
Cleared on tab close and on `logout()`. Keys:

| Key | Holds | Set by | Used by |
| --- | ----- | ------ | ------- |
| `auth_token` | JWT access token | login/admin-login/signup/refresh | `authInterceptor` (Bearer), `authGuard` |
| `refresh_token` | JWT refresh token | same | `authInterceptor` refresh |
| `account_id` | linked account id (or absent) | login/refresh/`setLinkedAccount` | dashboard/transfer/history |
| `holder_name` | display name | login/refresh/link-bank | navbars, greetings |
| `user_id` | user id | login (defaults `'1'`) | misc |
| `user_role` | `USER`/`ADMIN` | login | `isAdmin()`, guards |
| `username` | username | login | `verify-password` |

### localStorage (preferences only)
| Key | Holds | Set by |
| --- | ----- | ------ |
| `app-theme` | `light` \| `dark` UI theme | `ThemeService` |

> **No credentials or tokens are ever placed in `localStorage`** — only the non-sensitive theme choice (so it persists across tabs/restarts).

### Cookies
**Not used.** Auth is bearer-token in `sessionStorage`; the server is stateless (no `JSESSIONID`, no auth cookie). CSRF is therefore disabled by design.

### In-memory (not persisted)
`AuthService.isAuthenticatedSubject` (`BehaviorSubject<boolean>`) drives reactive UI (e.g. starting/stopping `InactivityService`); the `authInterceptor` keeps a module-level `isRefreshing` flag + `refreshedToken$` `BehaviorSubject` to coalesce concurrent refreshes.

## 21.2 Route guards (`guards/`, functional `CanActivateFn`)

| Guard | Rule | On failure | Applied to |
| ----- | ---- | ---------- | ---------- |
| `authGuard` | `AuthService.isAuthenticated()` (access token present) | redirect `/login` | `/dashboard`, `/transfer`, `/history`, `/rewards`, `/admin`, `/admin/users` |
| `userGuard` | block admins from user screens (`!isAdmin()`) | redirect `/admin` | `/dashboard`, `/transfer`, `/history`, `/rewards` |
| `adminGuard` | `isAdmin()` (role from token-derived session) | redirect `/dashboard` | `/admin`, `/admin/users` |

Routes are declared in `app.routes.ts`; protected routes list `canActivate: [authGuard, userGuard]` or `[authGuard, adminGuard]`. Public routes: `/login`, `/signup`, `/forgot-password`, `/admin/login`. Unknown paths (`**`) redirect to `/login`.

> Guards are **UX gating only** — the real enforcement is server-side (`SecurityConfig` + `JwtAuthFilter`). A tampered client cannot bypass `hasRole('ADMIN')` checks on the API.

## 21.3 HTTP interceptor (`authInterceptor`)

1. Reads `auth_token` and attaches `Authorization: Bearer <token>` to every outgoing request.
2. On **HTTP 401** for a non-auth endpoint *with* a refresh token: calls `AuthService.refreshToken()` **once** (shared across concurrent 401s via `isRefreshing` + `refreshedToken$`), then retries the original request with the new token.
3. If refresh fails: `AuthService.logout()` + navigate `/login`.
4. Auth endpoints (`/auth/login`, `/auth/refresh`, `/auth/signup`, …) are excluded from the refresh cycle (`isAuthEndpoint`).

## 21.4 JWT implementation (`config/JwtUtil`, `JwtAuthFilter`, `JwtAuthEntryPoint`)

* **Creation:** `JwtUtil.createToken` signs with `Keys.hmacShaKeyFor(secret.getBytes())`, algorithm **HS256**.
* **Access token claims:** `sub` = username, `role` (`USER`/`ADMIN`), `accountId` (nullable), `tokenType = access`, `iat`, `exp`. Lifetime `app.jwt.expiration = 600000 ms` (10 min).
* **Refresh token claims:** `sub` + `tokenType = refresh`, `iat`, `exp`. Lifetime `app.jwt.refresh-expiration = 604800000 ms` (7 days). Issued on login/admin-login/signup and **rotated** on every `/auth/refresh`.
* **Validation per request:** `JwtAuthFilter` (a `OncePerRequestFilter`) reads the Bearer header, `extractUsername`, loads the user (`CustomUserDetailsService` — also rejects non-`ACTIVE` users), and `validateToken` (subject match + `tokenType=access` + not expired) before placing an `Authentication` in the `SecurityContextHolder`. Failures are swallowed so the request proceeds unauthenticated and is then rejected by authorization rules.
* **Unauthorized response:** `JwtAuthEntryPoint` returns HTTP 401 with `{"errorCode":"AUTH-401","message":"Authentication required or token expired"}` — the signal the interceptor uses to refresh-and-retry.
* **Server statelessness:** `SecurityConfig` sets `SessionCreationPolicy.STATELESS`; no server session is created — identity comes solely from the JWT on each call.

## 21.5 Known trade-offs (storage/JWT)

* Tokens in `sessionStorage` are readable by JS, so they are exposed to XSS (mitigated by Angular's default escaping; no `httpOnly` cookie is used).
* No server-side token revocation/blacklist — a stolen access token is valid until expiry (≤10 min); refresh tokens are validated by signature+expiry only.
* JWT secret and admin/SMTP credentials live in `application.yaml` (should move to environment/secret management for production).
