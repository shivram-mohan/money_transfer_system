# 3. Registration (Signup) Flow

Signup is a 3-step, OTP-verified flow. **No admin approval is required** — the
account is created `ACTIVE` and the user is auto-logged-in. Bank linking happens
**later**, post-login.

```text
SignupComponent (3-step Material stepper)
  Step 1  AuthService.verifyAccount()      → POST /api/v1/auth/signup/verify-account → AuthController.verifyAccount() → OtpService.generateAndSendOtp(email,"SIGNUP")
  Step 2  AuthService.verifySignupOtp()    → POST /api/v1/auth/signup/verify-otp     → AuthController.verifySignupOtp() → OtpService.verifyOtp(email,otp,"SIGNUP")
  Step 3  AuthService.setPassword()        → POST /api/v1/auth/signup/set-password   → AuthController.setPassword() → UserService.completeSignup() → UserRepository.save() → users table
                                                                                     → auto-login: JwtUtil.generateToken + generateRefreshToken → AuthResponse
```

### Step 1 — `POST /api/v1/auth/signup/verify-account`
* **File / Method:** `AuthController.verifyAccount(VerifyAccountRequest)`
* **Input:** `{ username, email }` (`@NotBlank username`, `@Email email`)
* **Validations:** `userRepository.existsByUsername` → reject if taken; `existsByEmailIgnoreCase` → reject if email already used.
* **DB Ops:** `OtpService` upserts an `otp_tokens` row for the email (`SIGNUP`, 6-digit, expiry now+300s).
* **Output:** `OtpResponse { message, email=masked, success }`. Email dispatched asynchronously.
* **Exceptions:** `IllegalArgumentException` → `VAL-422` (username/email exists).

### Step 2 — `POST /api/v1/auth/signup/verify-otp`
* **File / Method:** `AuthController.verifySignupOtp(VerifyOtpRequest)`
* **Input:** `{ email, otp, purpose }`
* **Validations:** `OtpService.verifyOtp` checks purpose match, not expired, value match; consumes (deletes) the row on success.
* **Output:** `OtpResponse` ("OTP verified successfully. Please set your password.").
* **Exceptions:** invalid/expired OTP → `IllegalArgumentException` → `VAL-422`.

### Step 3 — `POST /api/v1/auth/signup/set-password`
* **File / Method:** `AuthController.setPassword(SetPasswordRequest)` → `UserService.completeSignup`
* **Input:** `{ username, email, name, password }` (all `@NotBlank`)
* **Validations:** re-checks username/email uniqueness inside `completeSignup`.
* **DB Ops:** inserts `users` row — `role=USER`, `status=ACTIVE`, `accountId=null`, BCrypt-hashed password, `createdBy/approvedBy="otp-verified"`.
* **Security:** password BCrypt-encoded (`PasswordEncoder`). Then auto-login: `userDetailsService.loadUserByUsername` → `JwtUtil.generateToken(userDetails,"USER",null)` + refresh token.
* **Output:** `201 CREATED` `AuthResponse { token, refreshToken, username, role=USER, accountId=null, holderName=name, expiresIn }`.

### Frontend form validation (`signup.component.ts`)
* `fullName` required, 2–100 chars; `username` required, 3–50; `email` required + email format; `otp` required, exactly 6; `password` required, min 6; client-side `password === confirmPassword` check.

> Note: `SignupRequest` (with `initialBalance`) DTO exists but is **not used** by the active 3-step flow; signup uses `VerifyAccountRequest` / `VerifyOtpRequest` / `SetPasswordRequest`.

# 4. OTP Verification Flow

Implemented in `service/OtpService.java` + `service/EmailService.java`,
persisted in `otp_tokens`.

```text
generateAndSendOtp(email, purpose)
  → secureRandom 6-digit code
  → upsert single otp_tokens row for email (otp, purpose, expiresAt = now + 300s)
  → EmailService.sendOtpEmail(...) @Async (otpMailExecutor) — API returns immediately

verifyOtp(email, otp, purpose)
  → load latest row for email (findTopByEmailOrderByIdDesc)
  → null? → false
  → purpose mismatch? → false
  → expired? → false
  → value mismatch? → false
  → else delete row (consume) → true
```

## OTP Generation
* **Method:** `String.format("%06d", secureRandom.nextInt(1_000_000))`
* **Length:** 6 digits (zero-padded).
* **Randomisation:** `java.security.SecureRandom`.

## OTP Storage
* **Table:** `otp_tokens`; **Columns:** `email` (unique, one row/email), `otp`, `purpose`, `expires_at`, `created_at`. The row is **reused** (updated) on each new request for that email.

## OTP Validation
* Latest row for the email; must match `purpose`, not be expired, and equal the submitted value. **Successful verification deletes the row** (single-use).

## Expiry Validation
* `expires_at = now + app.otp.expiration` (`300` seconds = 5 min). `isExpired()` = `now > expires_at`.

## Resend Flow
* Frontend re-calls step-1 endpoint (`signup.resendOtp` / `login.resendOtp`), which regenerates the code and overwrites the same row.

## Success Flow
* Returns `true`; caller proceeds (set password / issue JWT / reset password).

## Failure Flow
* Returns `false`; caller throws `IllegalArgumentException("Invalid or expired OTP")` → `VAL-422`.

**Email send failures are swallowed** (logged, not thrown) inside
`EmailService.sendOtpEmail` so the API still succeeds.

# 5. Login Flow (User — 2 steps + OTP)

```text
LoginComponent
  Step 1 onLogin    → AuthService.loginStep1()     → POST /api/v1/auth/login            → AuthController.loginStep1()
  Step 2 onVerifyOtp→ AuthService.loginVerifyOtp() → POST /api/v1/auth/login/verify-otp → AuthController.loginVerifyOtp()
```

## API Endpoints
* `POST /api/v1/auth/login` (credentials → OTP)
* `POST /api/v1/auth/login/verify-otp` (credentials + OTP → JWT)

## Controller Methods
* `AuthController.loginStep1(LoginOtpRequest)` and `AuthController.loginVerifyOtp(LoginVerifyRequest)`.

## Password Validation Logic
* Both steps call `authenticationManager.authenticate(UsernamePasswordAuthenticationToken)`, which uses `DaoAuthenticationProvider` + `CustomUserDetailsService` + `BCryptPasswordEncoder`. `CustomUserDetailsService` rejects non-`ACTIVE` users (`UsernameNotFoundException`).

## User Lookup Logic
* `userRepository.findByUsername(username)`; email used for OTP dispatch.

## JWT Generation & Claims
* `JwtUtil.generateToken(userDetails, role, accountId)`:
  * `sub` = username
  * `role` = `USER`/`ADMIN`
  * `accountId` = linked account id (null if not linked)
  * `tokenType` = `access`
  * `iat`, `exp` (now + 600000 ms = **10 min**)
  * Signature: **HS256** with `app.jwt.secret`.
* Refresh token (`generateRefreshToken`): `sub` + `tokenType=refresh`, `exp` = now + 604800000 ms (**7 days**).

## Response Structure
* `AuthResponse { token, refreshToken, username, role, accountId, holderName, expiresIn=600000 }`.

## Error Responses
* Bad credentials → `BadCredentialsException` → `AUTH-401` (401).
* Wrong/expired OTP → `VAL-422` (422).
* Non-active account → surfaces as auth failure.

## Sequence Diagram — Login

```text
User
  ↓ submit username/password
LoginComponent.onLogin()
  ↓ POST /api/v1/auth/login
AuthController.loginStep1()
  ↓ authenticationManager.authenticate()  → CustomUserDetailsService.loadUserByUsername()
  ↓ userRepository.findByUsername()
  ↓ OtpService.generateAndSendOtp(email,"LOGIN")  → EmailService (async) → SMTP
  ↓ OtpResponse(maskedEmail)
User  ← "OTP sent"
  ↓ submit OTP (+ stored creds)
LoginComponent.onVerifyOtp()
  ↓ POST /api/v1/auth/login/verify-otp
AuthController.loginVerifyOtp()
  ↓ authenticationManager.authenticate()   (re-auth)
  ↓ OtpService.verifyOtp(email,otp,"LOGIN") → consume row
  ↓ JwtUtil.generateToken + generateRefreshToken
  ↓ AuthResponse(token, refreshToken, accountId, ...)
AuthService.persistSession() → sessionStorage
Router → /dashboard
```

## Admin Login (no OTP)
* `POST /api/v1/auth/admin/login` → `AuthController.adminLogin(AuthRequest)`: authenticate, assert `ROLE_ADMIN`, issue tokens with `accountId=null`. Non-admin → `BadCredentialsException`.

## Forgot / Reset Password (2 steps, OTP `RESET`)
* `POST /api/v1/auth/forgot-password` → looks up user, sends `RESET` OTP to registered email (masked in response).
* `POST /api/v1/auth/reset-password` → verifies OTP, `UserService.resetPassword` BCrypt-encodes and saves the new password.

## Verify Password (re-auth, no token)
* `POST /api/v1/auth/verify-password` → authenticates only; success `OtpResponse`, failure → `IllegalArgumentException("Incorrect password")` → `VAL-422`. Used by the dashboard to gate revealing the balance (`PasswordPromptComponent`).

# 6. JWT Authentication Flow

## JWT Creation
* **File:** `config/JwtUtil.java`
* **Methods:** `generateToken(UserDetails, role, accountId)`, `generateRefreshToken(UserDetails)`, `createToken(claims, subject, ttl)`.

## JWT Validation
* **File:** `config/JwtUtil.java` — `validateToken` (username match + `tokenType=access` + not expired), `validateRefreshToken` (… + `tokenType=refresh`). Parsing via `Jwts.parserBuilder().setSigningKey(...).parseClaimsJws(...)`.

## Security Filter Chain (`config/SecurityConfig.java`)

```text
Request
  ↓
CorsFilter (CorsConfig — allows http://localhost:4200)
  ↓
JwtAuthFilter (OncePerRequestFilter, added before UsernamePasswordAuthenticationFilter)
  ↓ reads "Authorization: Bearer <jwt>"
  ↓ JwtUtil.extractUsername → userDetailsService.loadUserByUsername → JwtUtil.validateToken
  ↓ on success: SecurityContextHolder set with UsernamePasswordAuthenticationToken(authorities)
  ↓
authorizeHttpRequests rules
  ↓
Controller
```

* **Session policy:** `STATELESS`. **CSRF:** disabled.
* **Authorization rules:**
  * `/api/v1/auth/**` → `permitAll`
  * `GET /api/v1/users`, `PUT /api/v1/users/*/activate`, `PUT /api/v1/users/deactivate` → `hasRole("ADMIN")`
  * `POST /api/v1/accounts`, `PUT /api/v1/accounts/*/activate`, `PUT /api/v1/accounts/*/deactivate`, `GET /api/v1/accounts` → `hasRole("ADMIN")`
  * all other `/api/v1/**` → `authenticated`
  * anything else → `permitAll`

## Claims / Expiry / Algorithm
* Claims: `sub`, `role`, `accountId`, `tokenType`, `iat`, `exp`.
* Access expiry 10 min; refresh expiry 7 days. Algorithm **HS256**.

## Unauthorized Flow
* Missing/invalid token reaching a protected route → `JwtAuthEntryPoint.commence` returns **401** JSON `{"errorCode":"AUTH-401","message":"Authentication required or token expired"}`.
* The frontend `authInterceptor` catches 401 (on non-auth endpoints) and transparently calls `/auth/refresh`, retrying the original request with the new token; if refresh fails it logs out and routes to `/login`.

**Important caveat (as implemented):** `JwtAuthFilter` catches all exceptions
internally and simply continues the chain. The `accountId` in the token is **not
re-checked** against the requested resource — endpoints like
`GET /api/v1/accounts/{id}/balance` only require *authentication*, so any logged-in
user can request another account's id (see Security Analysis §13). The frontend
only ever sends the caller's own id.

# 7. Money Transfer Flow (most important)

```text
TransferComponent.onSubmit()
  ↓ (client checks: form valid, not self-transfer; looks up receiver name)
  ↓ ConfirmDialogComponent → executeTransfer()
TransferService.transfer()  → POST /api/v1/transfers
  ↓
TransferController.transfer(@Valid TransferRequest)
  ↓
TransferService.transfer()        [@Transactional]
  ├─ checkIdempotency(key)                 → transaction_logs.findByIdempotencyKey
  ├─ validateTransfer(request)             → amount>0, not cashback target, not self, both ACTIVE, sufficient balance
  └─ executeTransfer(request)
       ├─ from.debit(amount) / to.credit(amount)        (Account entity)
       ├─ accountRepository.save(from), save(to)        → optimistic @Version check
       ├─ syncBankDetailsBalance(from), (to)            → bank_details
       ├─ transactionLogRepository.save(SUCCESS log)    → transaction_logs
       └─ processRewardsSafely() → RewardService.processReward()  (errors swallowed)
  ↓
TransferResponse(SUCCESS, txnId, reward)
```

### Step: Controller — `TransferController.transfer`
* **File:** `controller/TransferController.java`
* **Input:** `TransferRequest { fromAccountId, toAccountId, amount, idempotencyKey }`, bean-validated (`@NotNull`, `@Positive`, `@DecimalMin 0.01`, `@DecimalMax 1000000.00`, `idempotencyKey @NotNull`).
* **Output:** `200 OK` with `TransferResponse`.

### Step: `TransferService.transfer` (the transaction boundary)
* **Method:** `@Transactional public TransferResponse transfer(TransferRequest)`
* **Transaction boundary:** the whole method is one transaction. On any non-duplicate exception it calls `transactionLogService.logFailedTransfer(...)` (which runs `REQUIRES_NEW`, so the FAILED row survives the rollback) and re-throws.

### Step: `checkIdempotency`
* `transactionLogRepository.findByIdempotencyKey(key)` → if present, throw `DuplicateTransferException` (**TRX-409**). A duplicate is NOT logged as failed.

### Step: `validateTransfer`
* amount null/≤0 → `IllegalArgumentException` (VAL-422)
* `toAccountId == CASHBACK_ACCOUNT_ID (9999999999)` → blocked (VAL-422)
* `from == to` → `IllegalArgumentException` (VAL-422)
* load both via `accountService.getAccountById` (throws `AccountNotFoundException` ACC-404 if missing)
* either not `ACTIVE` → `AccountNotActiveException` (**ACC-403**)
* `from.balance < amount` → `InsufficientBalanceException` (**TRX-400**)

### Step: `executeTransfer`
* **Tables Updated:** `accounts` (both rows), `bank_details` (if a matching row exists), `transaction_logs` (SUCCESS), `users` + `reward_ledger` (if reward earned).
* **SQL Operations:** `SELECT` accounts, `UPDATE accounts ... WHERE id=? AND version=?` (optimistic), `UPDATE bank_details`, `INSERT transaction_logs`, plus reward writes.
* **Rollback Logic:** any thrown exception rolls back the whole transfer transaction; the failure is separately recorded in its own `REQUIRES_NEW` transaction via `TransactionLogService.logFailedTransfer` (with `idempotencyKey=null` so the user can retry).
* **Exception Handling:** mapped by `GlobalExceptionHandler` to error codes (see below).
* **Concurrency Handling / Locking Strategy:** **optimistic locking** via `Account.@Version`. There is **no pessimistic lock** and **no explicit lock ordering**; two concurrent transfers on the same account that collide on `version` cause an `OptimisticLockException` → rolled back → surfaces via the global handler (`SYS-500`) and a FAILED log. **Deadlock-ordered locking: Not Implemented.**

### Reward sub-step
* `processRewardsSafely` wraps `RewardService.processReward` in try/catch — **a reward failure never fails the transfer** (returns null reward). `RewardService.processReward` is intentionally NOT `@Transactional` so it joins the transfer transaction.

### `bank_details` sync
* `syncBankDetailsBalance(account)` mirrors the new balance back to `bank_details` where `account_number == account.id`. Admin-created accounts (no bank row) are skipped.

# 8. Rewards Module Flow

Owner: `service/RewardService.java`, constants in `constants/RewardConstants.java`.

## Reward Calculation Formula
* Only if `amount > 100` (`MIN_REWARDABLE_AMOUNT`), sender is a registered user (`userRepository.findByAccountId(fromId)` present), not a self-transfer, and the directed pair hasn't been rewarded today.
* `basePoints = floor(amount / 100)` (`POINTS_EARN_DIVISOR = 100`).
* `pointsEarned = weekend ? basePoints * 2 : basePoints` (`WEEKEND_MULTIPLIER = 2`, weekend = Sat/Sun).

## Reward Accumulation
* `users.reward_points += pointsEarned`; `users.lifetime_reward_points += pointsEarned`.
* Inserts a `reward_ledger` row (`userId, from, to, transactionId, pointsEarned, weekendBonus, rewardDate=today`).
* `reachedRedeemThreshold` true when balance crosses 500 (`REDEEM_THRESHOLD`) on this transfer (drives a UI nudge).

## Once-per-day rule
* `rewardLedgerRepository.existsByFromAccountIdAndToAccountIdAndRewardDate(from,to,today)` — if already rewarded, returns `RewardResult.none("...already earned today's reward...")`.

## Reward Redemption  (`RewardService.redeem`, `@Transactional`)
* Endpoint `POST /api/v1/rewards/redeem` (`RewardController.redeem`, authenticated; user resolved from `Authentication.getName()`).
* Validations: `points >= 500`; `points <= balance`; user must have a linked `accountId`.
* Money movement: `cashbackAccount(9999999999).debit(points)` → `userAccount.credit(points)` (1 point = ₹1, `setScale(2)`); saves both; `syncBankDetailsBalance(userAccount)`.
* Inserts a SUCCESS `transaction_logs` row from CASHBACK → user (`idempotencyKey = "redeem-{userId}-{millis}"`).
* `users.reward_points = balance - points`.
* Response `RedeemResponse { redeemedPoints, amountCredited, remainingPoints, transactionId, message }`.

## Reward Profile  (`GET /api/v1/rewards/me`, `getProfile`)
* Returns `RewardProfileResponse { holderName, pointsBalance, lifetimePoints, redeemThreshold=500, canRedeem, progressPercent(0-100), weekendBonusActive }`.

## Reward Expiry
* **Not Implemented** — points never expire in the code.

## Tables Updated
* `users` (`reward_points`, `lifetime_reward_points`), `reward_ledger` (earn), `accounts` + `bank_details` + `transaction_logs` (redeem).

## Execution Order (earn)
1. eligibility checks → 2. compute points → 3. update `users` balances → 4. insert `reward_ledger` → 5. return `RewardResult` (surfaced inside `TransferResponse.reward`).

## CASHBACK account
* Seeded by `DataSeeder.seedCashbackAccount` with id `9999999999`, name `CASHBACK`, balance `1,000,000,000.00`. Its id is masked to `null`/"CASHBACK" in user-facing history (`AccountService.maskCashbackAccount`) and transfers **into** it are blocked.

# 10. Email Service Flow

* **Trigger Events:** OTP for `SIGNUP` / `LOGIN` / `RESET` (from `OtpService.generateAndSendOtp`). No other emails (no transfer receipts) are sent.
* **Service Invoked:** `EmailService.sendOtpEmail(toEmail, otp, purpose)` — annotated `@Async("otpMailExecutor")`.
* **SMTP Configuration (`application.yaml`):** host `smtp.gmail.com`, port `587`, STARTTLS required, `ssl.trust=smtp.gmail.com`, connect/read/write timeouts 30000 ms. Credentials are a Gmail account + app password (committed in `application.yaml` — see Security Analysis).
* **Email Template:** plain-text `SimpleMailMessage`; subject/body branch on purpose; body states validity = `otpExpirationSeconds/60` minutes (5).
* **Sending Logic:** `JavaMailSender.send(message)` on the `otpMailExecutor` pool (core 2 / max 5 / queue 100, thread prefix `otp-mail-`). The OTP is persisted *before* dispatch, so the API responds without waiting for SMTP.
* **Exception Handling:** the whole send is wrapped in try/catch and only logged — failures do **not** propagate to the user.
* **Retry Logic:** **Not Implemented** (no retry; a failed send just means no email).

# 13. Security Analysis

| Concern | Status | Implementation detail |
| ------- | ------ | --------------------- |
| Authentication | **Implemented** | Spring Security `DaoAuthenticationProvider` + `CustomUserDetailsService`; only `ACTIVE` users authenticate; 2-factor (password + email OTP) for user login. |
| Authorization | **Implemented (role-based)** | `hasRole("ADMIN")` matchers in `SecurityConfig`; `userGuard`/`adminGuard` on the client. **No per-resource ownership check** on account endpoints (see below). |
| JWT Security | **Implemented** | HS256, signed with `app.jwt.secret`; access 10 min, refresh 7 days, rotated on refresh; `tokenType` distinguishes access vs refresh. |
| Password Storage | **Implemented** | BCrypt (`BCryptPasswordEncoder`) for all users incl. admin. |
| Encryption (data at rest / field-level) | **Not Implemented** | No column/field encryption; TLS termination is assumed external. |
| Session Handling | **Implemented (stateless)** | Server `SessionCreationPolicy.STATELESS`; client uses `sessionStorage` + inactivity auto-logout (8-min warning / 10-min logout). |
| CSRF | **Not Implemented (disabled by design)** | `csrf().disable()` — acceptable for a stateless Bearer-token API. |
| CORS | **Implemented** | `CorsConfig` allows origin `http://localhost:4200`, credentials, common methods/headers. |
| SQL Injection Protection | **Implemented** | All access via Spring Data JPA / parameterised `@Query`; no string-concatenated SQL (the only raw SQL is fixed DDL in `DataSeeder`). |
| XSS Protection | **Partial / framework-default** | Angular template auto-escaping; no backend output encoding/CSP headers configured. |
| Rate Limiting | **Not Implemented** | No throttling on login/OTP/transfer endpoints. |

### Notable security observations (as-implemented, not assumed)
* **Broken object-level authorization (IDOR):** `GET /api/v1/accounts/{id}` and `/{id}/balance|transactions|statement` require only authentication, not that `{id}` belongs to the caller (the token's `accountId` claim is never compared to `{id}`). Any logged-in user can read another account by id.
* **Secrets in source:** `application.yaml` contains the DB password, the JWT secret, and a live Gmail app password. These should be externalised.
* **JWT secret length:** the configured secret is ~61 ASCII chars (≈488 bits), satisfying HS256's 256-bit minimum for `Keys.hmacShaKeyFor`.
* **`UserController.getUserById` / `linkBankAccount`** are only `authenticated` (not admin-restricted), so any user can fetch any user profile by id.

# 17. End-to-End Transfer Walkthrough

**Scenario:** John (linked bank account `1001001001`, balance ₹50,000) transfers
₹10,000 to Jane (account `1001001002`, balance ₹75,000). Assume a weekday.

### 1. Incoming Request Payload (`POST /api/v1/transfers`)
```json
{
  "fromAccountId": 1001001001,
  "toAccountId": 1001001002,
  "amount": 10000.00,
  "idempotencyKey": "1718972400000-ab12cd34ef"
}
```
Header: `Authorization: Bearer <John's access JWT>`.

### 2. JWT Validation
`JwtAuthFilter` validates the token, loads John's `UserDetails`, sets the
SecurityContext. `/api/v1/transfers` requires only `authenticated` → passes.

### 3–6. Validation (inside `TransferService.transfer`)
* **Idempotency:** `findByIdempotencyKey("1718972400000-ab12cd34ef")` → none → continue.
* **Amount:** 10000 > 0 ✓, ≤ 1,000,000 ✓; target ≠ CASHBACK ✓; from ≠ to ✓.
* **Account validation:** both accounts loaded; both `ACTIVE` ✓.
* **Balance check:** 50,000 ≥ 10,000 ✓.

### Before State
| Table | Row | Value |
| ----- | --- | ----- |
| accounts | 1001001001 | balance 50000.00, version v |
| accounts | 1001001002 | balance 75000.00, version w |
| users (John) | reward_points | (say) 120 |

### 7. Transaction Creation / 8. Reward / 10. DB Updates (during)
* `from.debit(10000)` → 40,000; `to.credit(10000)` → 85,000.
* `UPDATE accounts SET balance=40000.00, version=v+1 WHERE id=1001001001 AND version=v`
* `UPDATE accounts SET balance=85000.00, version=w+1 WHERE id=1001001002 AND version=w`
* `UPDATE bank_details SET balance=40000.00 WHERE account_number=1001001001`
* `UPDATE bank_details SET balance=85000.00 WHERE account_number=1001001002`
* `INSERT transaction_logs (id=UUID, from=1001001001, to=1001001002, amount=10000.00, status=SUCCESS, idempotency_key=..., created_on=now)`
* **Reward:** amount 10000 > 100 ✓, sender is registered ✓, pair not rewarded today ✓. `basePoints = floor(10000/100) = 100`, weekday → 100 points. `UPDATE users SET reward_points=220, lifetime_reward_points+=100`. `INSERT reward_ledger(...points_earned=100, weekend_bonus=false, reward_date=today)`. (If John had been below 500 and crossed it, `reachedRedeemThreshold=true`.)

### 9. Audit Logging
The SUCCESS `transaction_logs` row IS the audit record; `LoggingAspect` also logs
service entry/exit/timing. A FAILED row would only be written on the error path.

### 11. Commit
The single `@Transactional` boundary commits all of the above atomically. The
reward write joined the same transaction (it is not separately `@Transactional`),
so it commits together; had it thrown, `processRewardsSafely` would have caught it
and committed the transfer with `reward=null`.

### 12. Response Payload (`200 OK`)
```json
{
  "TransactionId": "<uuid>",
  "status": "SUCCESS",
  "message": "Transfer completed successfully",
  "debitedFrom": 1001001001,
  "creditedTo": 1001001002,
  "amount": 10000.00,
  "reward": {
    "rewarded": true,
    "pointsEarned": 100,
    "weekendBonus": false,
    "pointsBalance": 220,
    "lifetimePoints": <updated>,
    "reachedRedeemThreshold": false,
    "message": "You earned 100 reward points."
  }
}
```

### After State
| Table | Row | Value |
| ----- | --- | ----- |
| accounts | 1001001001 | balance 40000.00, version v+1 |
| accounts | 1001001002 | balance 85000.00, version w+1 |
| bank_details | 1001001001 / 1001001002 | 40000.00 / 85000.00 |
| transaction_logs | new | SUCCESS, 10000.00 |
| users (John) | reward_points | 220 |
| reward_ledger | new | 100 pts, weekday |

### Failure variant (insufficient balance)
If John tried ₹60,000: `validateTransfer` throws `InsufficientBalanceException`;
the main transaction rolls back (no balance change); `TransactionLogService.logFailedTransfer`
writes a FAILED row (`idempotency_key=null`) in a **new** transaction;
`GlobalExceptionHandler` returns `400 TRX-400`. The FAILED row appears in **John's**
history only (not Jane's), per `findVisibleByAccountId`.

# 18. Interview / Test Questions (with answers)

**Q1. Where is the transaction boundary for a transfer, and what happens to the failed-transfer log on rollback?**
A: `TransferService.transfer` is `@Transactional`. On failure the whole transfer rolls back, but `TransactionLogService.logFailedTransfer` runs with `Propagation.REQUIRES_NEW`, so the FAILED row commits in its own transaction and survives the rollback.

**Q2. How is concurrency handled on the same account?**
A: Optimistic locking via `Account.@Version`. Conflicting concurrent updates fail the `version`-guarded UPDATE → `OptimisticLockException` → rollback + FAILED log. No pessimistic locks or ordered locking are implemented.

**Q3. Why doesn't a broken reward calculation fail the transfer?**
A: `RewardService.processReward` is deliberately **not** `@Transactional`, and `TransferService.processRewardsSafely` wraps it in try/catch returning `null`. So a reward error neither marks the transaction rollback-only nor reaches the client as a failure.

**Q4. How is idempotency enforced, and why is the key not stored on failed transfers?**
A: `transaction_logs.idempotency_key` is unique; `checkIdempotency` rejects a replay with `DuplicateTransferException` (TRX-409). Failed logs store `null` for the key so the user can retry the same transfer after fixing the cause without hitting the unique constraint.

**Q5. What are the reward rules?**
A: Earn `floor(amount/100)` points only if amount > ₹100, sender is a registered user, not a self-transfer, and the from→to pair hasn't earned today; points double on weekends (Sat/Sun). Redeem ≥500 points at 1 point = ₹1 from the CASHBACK account (id 9999999999). Points don't expire.

**Q6. How does the 2-step user login differ from admin login?**
A: User login is two calls (`/auth/login` then `/auth/login/verify-otp`) with an email OTP between them. Admin login (`/auth/admin/login`) authenticates once with no OTP and asserts `ROLE_ADMIN`.

**Q7. What's in the JWT and how long does it live?**
A: Claims `sub`, `role`, `accountId`, `tokenType`, `iat`, `exp`. Access token 10 min, refresh token 7 days, HS256. Refresh rotates both tokens.

**Q8. How does the frontend handle an expired access token?**
A: The backend returns 401 (`JwtAuthEntryPoint`). `authInterceptor` does a single-flight call to `/auth/refresh`, retries queued requests with the new token, and logs out if refresh fails.

**Q9. How is an OTP stored and consumed?**
A: One reusable row per email in `otp_tokens` (6-digit `SecureRandom`, 5-min expiry). `verifyOtp` checks purpose/expiry/value and **deletes** the row on success (single-use).

**Q10. Is there a beneficiary module?**
A: No dedicated beneficiary entity/endpoints. Transfers target an arbitrary account id (resolved via `GET /accounts/{id}` for confirmation), and users link their own bank account via `POST /users/link-bank`.

**Q11. How does bank linking prove ownership?**
A: The supplied `accountNumber` must exist in `bank_details`, its `email` must match the user's OTP-verified email, and it must not already be `registered`. It then seeds an `accounts` row with the bank balance.

**Q12. Where does the schema come from given schema.sql is empty?**
A: Hibernate `ddl-auto: update` generates tables from the `@Entity` classes; `DataSeeder` (a `CommandLineRunner`) seeds the admin, bank records, and CASHBACK account and runs small migrations on startup.

**Q13. Name a real security gap in the current code.**
A: Account-read endpoints (`/accounts/{id}/...`) check only authentication, not ownership (the token's `accountId` is never compared to the path id) — an IDOR. Also, DB/JWT/Gmail secrets are committed in `application.yaml`, and there's no rate limiting.

**Q14. What happens to the CASHBACK account id in user history?**
A: `AccountService.maskCashbackAccount` replaces id `9999999999` with `null` and labels it `"CASHBACK"` inside a read-only transaction, so the corporate id is never exposed.

**Q15. Which failed transfers appear in whose history?**
A: `findVisibleByAccountId` shows a transaction to the sender always, but to the receiver only if status ≠ FAILED — so a failed transfer surfaces only in the sender's history.
